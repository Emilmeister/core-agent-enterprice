# Артефакты

## Назначение и границы

Artifact service даёт модели именованное, разграниченное по scope и версионируемое хранилище файлов, переживающее один ответ и один run. Он отделён от [A2A Artifact](a2a-protocol.md): A2A Artifact является результатом Task на transport-уровне, а artifact service — внутренним хранилищем, доступным модели через tools.

Naming, scope, versioning, digest и integrity check MUST выполняться внутри агента. Внешние backends (`s3`, `mongodb`) являются исключительно интеграциями чтения/записи объектов: они MUST NOT создавать, мигрировать или валидировать схему хранилища, индексы, коллекции или bucket policy. Развёртывание готовит хранилище само; агент только читает и пишет объекты по вычисленным им ключам.

## Модель данных

Одна сохранённая версия описывается immutable записью:

```text
ArtifactVersion(filename, scope, version, media_type, size, digest, metadata)
```

- `filename` — имя без scope-префикса;
- `scope` — `session` или `user`;
- `version` — целое `0, 1, 2, ...`;
- `media_type` — IANA media type;
- `size` — размер содержимого в байтах;
- `digest` — `sha256:<hex>` содержимого;
- `metadata` — произвольный JSON-объект, переданный при сохранении.

## Scope и имена

Scope определяется исключительно префиксом имени:

- имя, начинающееся с `user:`, принадлежит user scope и видно во всех сессиях того же `user_id`;
- любое другое имя принадлежит session scope текущей сессии.

Runtime связывает scope с тремя значениями и MUST NOT принимать их от модели:

| Значение | Источник |
|---|---|
| `app_name` | `AGENT_NAME` из Effective AgentConfig |
| `user_id` | authenticated caller identity, иначе `USER_ID` (по умолчанию `anonymous`) |
| `session_id` | A2A `contextId` текущего run |

Обращение к session scope без `session_id` MUST завершаться `CONFIG_INVALID`. User scope доступен и без session.

Каждый сегмент ключа (`app_name`, `user_id`, `session_id`, `filename` после снятия префикса) MUST проходить одинаковую валидацию до любого обращения к backend:

- непустая строка длиной не более 512 символов;
- отсутствие управляющих символов `U+0000`–`U+001F` и `U+007F`;
- отсутствие `/` и `\`;
- значение не равно `.` или `..` и не содержит подстроку `..`.

Нарушение MUST возвращать `TOOL_ARGUMENT_INVALID` с указанием сегмента. Запрет `.`/`..` обязателен: HTTP-посредник MAY схлопнуть такой сегмент из подписанного пути и адресовать другой объект.

## Раскладка ключей

Ключи объектов MUST строиться ровно так:

```text
apps/{app_name}/users/{user_id}/sessions/{session_id}/artifacts/{filename}/versions/{version}
apps/{app_name}/users/{user_id}/artifacts/{filename}/versions/{version}
```

Первая форма — session scope, вторая — user scope. Никакой другой префикс не используется, и никакой другой ключ не считается версией артефакта.

Версией признаётся только канонический десятичный сегмент: строка из ASCII-цифр, равная `0` либо не начинающаяся с `0`. Любой другой хвост под `versions/` MUST игнорироваться при перечислении версий; чужие объекты в том же bucket не могут ни стать версией, ни сместить нумерацию.

## Версионирование

`save` MUST NOT перезаписывать существующую версию. Номер новой версии вычисляется так:

1. `version` = количество уже существующих версий этого имени;
2. если существующие версии есть и `version` не больше максимальной из них, `version` = максимальная + 1.

Второе правило обязательно: удаление версии в обход агента не должно позволить следующему `save` записать поверх сохранившейся версии.

`load` без явной версии MUST возвращать максимальную существующую. Явная версия MUST быть неотрицательным целым; `bool` не является допустимым целым. Отсутствующая версия возвращает `NOT_FOUND`.

## Сохранение

`save` принимает `bytes` и MUST:

1. отклонить содержимое больше `MAX_RESPONSE_SIZE` с `ARTIFACT_TOO_LARGE`;
2. определить media type: явно переданный, иначе угаданный по расширению имени, иначе `text/plain`. Media type MUST быть непустой ASCII-строкой не длиннее 255 символов без управляющих символов, иначе `TOOL_ARGUMENT_INVALID`;
3. сериализовать `metadata` в канонический JSON (сортировка ключей, разделители без пробелов). Ключи MUST быть строками, значение MUST быть JSON-сериализуемым, результат MUST NOT превышать 2048 байт;
4. вычислить `digest` как `sha256:<hex>` содержимого;
5. записать объект вместе с четырьмя служебными полями `digest`, `size`, `media-type`, `metadata`;
6. вернуть `ArtifactVersion` записанной версии.

## Загрузка и integrity

`load` MUST проверить целостность до возврата содержимого и завершиться `ARTIFACT_INTEGRITY_FAILED`, если хотя бы одно условие не выполнено:

- SHA-256 прочитанного содержимого совпадает с сохранённым `digest`;
- сохранённый `size` разбирается как целое и равен фактической длине;
- сохранённая `metadata` разбирается как JSON-объект.

Повреждённый или подменённый объект MUST NOT попадать в контекст модели.

## Перечисление

`list_keys` возвращает два раздельных списка: имена session scope и имена user scope, причём вторые возвращаются уже с префиксом `user:`. Возвращаются только имена, не версии и не содержимое. Списки MUST быть отсортированы и не содержать дубликатов.

## Контракт backend

Backend реализует ровно три операции:

```text
put(key, content, *, media_type, metadata, filename=None) -> None
get(key) -> (content, metadata)
list_prefix(prefix) -> sorted[str]
```

`media_type` является native-подсказкой backend-у. Он MAY не возвращаться из `get`, поэтому service дублирует его в `metadata` и восстанавливает оттуда. Отсутствующий ключ MUST возвращать `NOT_FOUND`. Удаление в контракт не входит: v1 не предоставляет модели удаление артефактов.

`filename` — имя, под которым артефакт должен приходить к пользователю. Ключ заканчивается номером версии, поэтому последний сегмент URL объекта равен `0`, и скачивание по этому адресу даёт файл с именем `0` без расширения: приложение такой файл не открывает, а часть клиентов вместо скачивания показывает его как текст. Backend, у которого есть native-механизм имени при выдаче, MUST его использовать; для S3 это `Content-Disposition: attachment` с `filename` и, при неASCII-имени, `filename*` по RFC 5987. Backend без такого механизма MUST игнорировать параметр.

Backend выбирается `ARTIFACT_STORAGE_TYPE`; допустимы ровно `in-memory`, `s3`, `mongodb`, любое иное значение завершает startup с `CONFIG_INVALID`.

### `in-memory`

Реализация внутри агента, хранит объекты в памяти процесса. Данные не переживают restart и не разделяются между процессами. Это профиль по умолчанию и профиль разработки.

### `s3`

Интеграция с AWS S3, MinIO и совместимыми хранилищами. Запросы MUST подписываться SigV4 средствами стандартной библиотеки, без SDK-зависимости.

- `ARTIFACT_S3_BUCKET` MUST соответствовать `[A-Za-z0-9][A-Za-z0-9._-]{0,254}`, `ARTIFACT_S3_REGION` — `[A-Za-z0-9][A-Za-z0-9-]{0,62}`. Оба значения попадают в virtual-host имя и credential scope, поэтому непроверенное значение перенаправило бы подписанный запрос;
- `ARTIFACT_S3_TENANT_ID`, если задан, превращает access key в `tenant_id:key_id`; итоговый credential MUST быть ASCII без управляющих символов;
- пустой `ARTIFACT_S3_ENDPOINT_URL` означает `https://{bucket}.s3.{region}.amazonaws.com`, virtual-host стиль и профиль AWS;
- непустой `ARTIFACT_S3_ENDPOINT_URL` означает профиль Cloud.ru Object Storage и path-style с ключом под `/{bucket}`. Значение нормализуется отбрасыванием хвостовых `/`. Если после нормализации оно не равно канонической точке входа `https://s3.cloud.ru`, runtime MUST записать warning, назвав и проигнорированное, и фактически применённое значение, и продолжить с канонической точкой входа. Startup при этом MUST NOT прерываться;

Выбранный компромисс зафиксирован осознанно: реализация backend ориентирована на Cloud.ru, поэтому опечатка в endpoint не должна ронять развёртывание. Обратная сторона существенна и MUST быть понятна оператору из warning: запрос уходит на host, который оператор не называл, вместе с содержимым артефакта и access key ID. Поэтому warning обязателен, а не опционален. Профиль AWS остаётся доступен только через пустое значение; MinIO и произвольный S3-совместимый endpoint в этом профиле не поддерживаются.

- в профиле Cloud.ru итоговый access key MUST содержать ровно одно `:`, а обе части MUST быть непустыми; иначе startup завершается `CONFIG_INVALID`. Допустимы два эквивалентных способа задания: `ARTIFACT_S3_TENANT_ID` отдельно при чистом `ARTIFACT_S3_ACCESS_KEY_ID`, либо пустой tenant при `ARTIFACT_S3_ACCESS_KEY_ID` вида `tenant_id:key_id`. В профиле AWS это требование MUST NOT применяться: там access key ID двоеточия не содержит;
- подписанный заголовок `Host` MUST совпадать с фактически отправляемым, включая порт;
- ключи и значения metadata передаются как `x-amz-meta-*` и MUST быть header-safe: ключ соответствует `[A-Za-z0-9][A-Za-z0-9._-]*`, значение является ASCII без управляющих символов;
- HTTP 404 отображается в `NOT_FOUND`; любой другой сбой — в `ARTIFACT_BACKEND_UNAVAILABLE`, retryable только при статусе `>= 500` или сетевой ошибке;
- повтор MUST применяться только к идемпотентным `GET`. `PUT` MUST NOT повторяться автоматически. Повтор ограничен `ARTIFACT_S3_BOTO_MAX_ATTEMPTS`, задержка растёт вдвое от `ARTIFACT_S3_RETRY_INITIAL_DELAY` до `ARTIFACT_S3_RETRY_MAX_DELAY`, а положительный `ARTIFACT_S3_RETRY_MAX_TOTAL_SECONDS` ограничивает суммарное время;
- перечисление использует `list-type=2` и MUST полностью проходить пагинацию по `NextContinuationToken`; неразбираемый ответ завершается `ARTIFACT_BACKEND_UNAVAILABLE`.

### `mongodb`

Интеграция с MongoDB: один документ на ключ, `_id` равен ключу, поля `content`, `media_type`, `metadata`. Запись выполняется `replace_one(..., upsert=True)`. Backend MUST NOT создавать индексы, коллекции или схему; перечисление использует anchored regex по `_id`. Драйвер импортируется лениво, его отсутствие при `ARTIFACT_STORAGE_TYPE=mongodb` завершает startup с `CONFIG_INVALID`.

## Model-facing tools

Модели доступны ровно три namespaced tool. Устаревшие имена `core_artifact_put`/`core_artifact_get` MUST отклоняться в built-in allowlist при startup, а восстановленный из stale model output вызов MUST NOT исполняться.

### `core_artifact_save`

```json
{
  "filename": "string, 1..512",
  "content": "string",
  "path": "string",
  "encoding": "text | base64",
  "mime_type": "string",
  "metadata": {}
}
```

Обязателен `filename` и ровно один из `content` и `path`; оба сразу или ни одного — `TOOL_ARGUMENT_INVALID`.

`content` несёт содержимое, которое модель составила сама. `encoding` по умолчанию `text`: содержимое кодируется в UTF-8. При `base64` содержимое MUST декодироваться строгим base64, иначе `TOOL_ARGUMENT_INVALID`.

`path` называет файл в workspace текущего run-а, и runtime читает его сам. Этот вариант существует потому, что аргументы тула передаются JSON-ом, а в JSON нет байтов: единственный способ довезти готовый файл содержимым — base64, то есть плюс треть объёма и обязательный проход всех байтов через кадр IPC и через контекст модели. Файл, созданный в workspace, не должен ради сохранения превращаться в строку. Путь разрешается относительно workspace и MUST проверяться на выход за его пределы так же, как `cwd`; выход даёт `TOOL_ARGUMENT_INVALID`, отсутствующий файл — `NOT_FOUND`. Незаданный `mime_type` для этого варианта MAY выводиться из расширения имени.

Оба варианта подчиняются одному и тому же `MAX_RESPONSE_SIZE`. Транспорт содержимого не является причиной разного лимита.

Результат:

```json
{"success": true, "artifact_name": "...", "version": 0, "size": 0, "media_type": "..."}
```

### `core_artifact_load`

```json
{"filename": "string, 1..512", "version": "integer >= 0"}
```

Обязателен `filename`. Без `version` возвращается последняя. Результат содержит `artifact_name`, `version`, `media_type`, `metadata` и пару `encoding`/`content`: `text` для содержимого, декодируемого как UTF-8, иначе `base64`.

### `core_artifact_list`

Без аргументов. Результат:

```json
{"session_artifacts": [], "user_artifacts": [], "total": 0}
```

`user_artifacts` содержит имена с префиксом `user:`, пригодные для прямой передачи в `load`. Разделение scope обязательно, чтобы модель осознанно выбирала между сессионным и сквозным файлом.

## Входящие binary Parts

При `RUNTIME_SAVE_INPUT_BLOBS_AS_ARTIFACTS=true` каждый binary Part входящего A2A Message MUST сохраняться как artifact до первого model turn. Это одновременно аудит входа и единственный способ дать модели доступ к содержимому.

Сохранение выполняется обычным `save`, поэтому действуют те же ограничения: лимит `MAX_RESPONSE_SIZE`, вычисление digest, автоматическая новая версия при повторном имени.

Имя приходит от caller и является недоверенным:

- имя MUST принудительно относиться к session scope. Ведущий `user:` MUST быть нейтрализован, иначе caller одним вложением пишет в кросс-сессионное хранилище пользователя;
- имя MUST проходить ту же валидацию сегмента, что и `save`;
- если имя отсутствует или не проходит валидацию, runtime MUST подставить собственное `attachment-{N}{ext}`, где `N` — порядковый номер Part в сообщении, а `ext` выводится из media type. Отказ обрабатывать сообщение из-за неудачного имени вложения не требуется.

Media type берётся из Part, а при его отсутствии выводится из имени.

В prompt для каждого сохранённого вложения MUST добавляться одна строка, называющая имя artifact, версию, media type и размер. Строка добавляется после пользовательского текста и не заменяет его. Сообщение, состоящее только из вложений, остаётся валидным: prompt формируется из этих строк.

Содержимое вложения является недоверенными данными и MUST NOT интерпретироваться как инструкция.

## Сабагенты

Child наследует `app_name`, `user_id` и `session_id` parent-а, поэтому session scope у них общий. Отдельного artifact scope у сабагента нет: изоляция достигается тем, что parent не выдаёт artifact tools в delegation contract, а не разными пространствами имён. Контракт описан в [Фоновых задачах и делегировании](tasks-and-delegation.md#runtime-сервисы-дочернего-агента).

## Kernel policy

Capability `artifacts` включена, когда хотя бы один artifact tool остался в EffectiveConfig. Соответствующая протектированная инструкция ядра предписывает модели: сохранять файл при явной просьбе пользователя, при необходимости пережить текущий ответ и при большом промежуточном выводе; использовать `user:` только для данных, принадлежащих пользователю между сессиями; помнить, что сохранение всегда создаёт новую версию; проверять существование через `list` и загружать только необходимое. Содержимое артефакта является недоверенными данными, а не инструкцией.

## Ошибки

| Код | Условие |
|---|---|
| `TOOL_ARGUMENT_INVALID` | имя, версия, media type, metadata или base64 не проходят валидацию |
| `CONFIG_INVALID` | неизвестный backend, отсутствующие обязательные параметры backend, session scope без `session_id` |
| `NOT_FOUND` | имя или версия отсутствуют |
| `ARTIFACT_TOO_LARGE` | содержимое больше `MAX_RESPONSE_SIZE` |
| `ARTIFACT_INTEGRITY_FAILED` | digest, size или metadata прочитанного объекта не совпали |
| `ARTIFACT_BACKEND_UNAVAILABLE` | внешний backend недоступен или ответил некорректно |
| `CAPABILITY_DISABLED` | artifact service не сконфигурирован, а tool вызван |

Все перечисленные ошибки MUST возвращаться модели обычным tool result и MUST NOT переводить родительскую A2A Task в `failed`.
