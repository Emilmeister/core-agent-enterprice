# Безопасность и надёжность

## Trust boundaries

Доверенными являются только safety-инварианты ядра и валидированные PlatformConfig/AgentConfig. Следующие источники MUST считаться недоверенными:

- prompt;
- AgentProfilePrompt;
- memory content, metadata и derived graph results;
- skill instructions, scripts и resources;
- MCP metadata, tool schemas и outputs;
- A2A peer Messages, Agent Cards и Artifacts;
- terminal output;
- содержимое файлов workspace;
- текст, полученный из сети.

Недоверенный текст не может менять policy или получать секреты только через prompt injection.

## Local process trust boundary

Python, terminal и фоновые команды MUST проходить обязательные mount/PID/IPC/network ограничения Bubblewrap в одном Kubernetes Pod по [Среде исполнения](execution-environment.md). Отдельные PTY/process groups сами по себе не обеспечивают security isolation. Runtime MUST отказать до запуска недоверенного кода, если обязательный профиль недоступен; fallback к общей filesystem/network среде сервера запрещён.

## Секреты

- Конфигурация содержит только ссылки на секреты; входящий Message не переносит их вовсе.
- Secret resolver работает после policy check и непосредственно перед использованием.
- Значения секретов MUST NOT попадать в model context, events, logs, errors или artifacts.
- Output проходит redaction известных значений и распространённых credential patterns.
- Модель получает только факт доступности секрета, если ей не требуется само значение для tool schema; предпочтительно secret injection выполняет adapter.

## Filesystem

- Все пути нормализуются и проверяются после разрешения symlinks.
- Проверка path traversal выполняется до чтения и до записи.
- `apply_patch` должен быть атомарным на уровне одного patch: либо применены все hunks, либо ни одного.
- Ядро MUST различать изменения этого запуска и существующие пользовательские изменения; оно MUST NOT откатывать последние без явного запроса.

## Процессы

- Каждый процесс принадлежит одному `run_id`, agent ID и TerminalSession.
- Output читается без неограниченного накопления в памяти.
- Тайм-аут завершает process tree, а не только родительский PID, если это поддерживается ОС.
- Интерактивный stdin адресуется непрозрачным session ID.
- После терминального состояния не должно оставаться процессов, кроме явно зафиксированного сбоя cleanup.

## Идемпотентность и side effects

- Ядро сохраняет tool call intent до исполнения.
- Для внешних мутаций adapter SHOULD передавать idempotency key из `tool_call_id`.
- Неопределённый исход мутирующего call MUST возвращаться как `SIDE_EFFECT_UNKNOWN`, а не автоматически повторяться.
- Итоговый ответ обязан сообщить о возможном частичном эффекте.

## Ошибки

Ошибка имеет стабильный `code`, безопасный `message`, `retryable` и внутренний correlation ID. Минимальный набор кодов:

- `INVALID_REQUEST`;
- `MODEL_UNAVAILABLE`, `MODEL_CAPABILITY_MISSING`;
- `MCP_CONNECTION_FAILED`, `MCP_PROTOCOL_ERROR`;
- `SKILL_INVALID`, `SKILL_RESOURCE_MISSING`, `SKILL_RESOURCE_INVALID`,
  `SKILL_ACTIVATION_BOUNDARY`;
- `TOOL_NAME_COLLISION`, `TOOL_ARGUMENT_INVALID`, `TOOL_EXECUTION_FAILED`;
- `POLICY_DENIED`;
- `EXECUTION_ENVIRONMENT_UNAVAILABLE`, `EXECUTION_ENVIRONMENT_COMPROMISED`;
- `BUDGET_EXCEEDED`, `CONTEXT_UNRECOVERABLE`;
- `SIDE_EFFECT_UNKNOWN`, `INTERNAL_ERROR`;
- `SESSION_CONFLICT`, `LEASE_LOST`, `CHECKPOINT_INVALID`;
- `CONFIG_INVALID`, `CONFIG_CONFLICT`, `CAPABILITY_DISABLED`, `REQUIRED_CAPABILITY_MISSING`, `TOOL_FILTER_EMPTY`;
- memory errors `MEMORY_FILE_TOO_LARGE`, `MEMORY_CONFLICT`, `MEMORY_INVALID`;
- `SKILL_INTEGRITY_FAILED`, `EXTENSION_REVOKED`;
- `MODEL_ROUTE_UNAVAILABLE`;
- `TASK_NOT_FOUND`, `TASK_NOT_CANCELABLE`, `TASK_NOTIFICATION_FAILED`;
- `A2A_VERSION_UNSUPPORTED`, `A2A_EXTENSION_REQUIRED`.

Stack traces, raw provider errors и секретные arguments MUST NOT попадать в публичный message. Они MAY сохраняться в защищённом operator log по correlation ID.

## Crash recovery

Durable continuation является свойством целевого runtime. Ядро MUST:

- дописывать audit events до публикации внешнему клиенту либо использовать атомарный эквивалент;
- восстанавливать незавершённые runs из event log и последнего проверенного checkpoint;
- сохранять сведения о начатых внешних side effects;
- автоматически продолжать только доказуемо безопасные или идемпотентные операции;
- переводить неоднозначную внешнюю мутацию в reconciliation, `WAITING_INPUT` или `ABORTED`;
- сохранять pending input с исходными IDs и scopes.

## Multi-tenancy

- Tenant identity устанавливается authenticated transport context, не prompt.
- Stores, caches, terminal sessions/workspaces, MCP connections и artifact URLs MUST быть tenant-scoped. Подсистема памяти отвечает за tenant isolation Markdown/BM25/vector/graph data.
- Cross-tenant identifiers возвращают not-found semantics, если раскрытие существования запрещено.
- Quotas применяются до выделения дорогого model/execution ресурса.
- Child runs всегда наследуют tenant и не могут сменить его через arguments.
- Authenticated deployment восстанавливает только свою configured company.
  Tenant чужой persisted row не является разрешением использовать текущий
  model/provider, process, remote credentials либо cleanup/push executor.
  Legacy rowless upload manifest без доказанного tenant сохраняется для
  reconciliation; company не выводится из UUID, имени файла или содержимого.

## Supply chain

- Remote skill/MCP artifacts проверяются по integrity и trust policy.
- Dependency snapshot и signatures сохраняются в audit.
- Revocation feed MAY заблокировать новый run или приостановить активный.
- Provider и adapter versions фиксируются для воспроизводимости; security patches могут обновляться с явно записанной migration boundary.

## Policy versioning

Каждое решение policy хранит policy version и matched rules. Новая более строгая policy применяется к ещё не начатым actions активного run. Уже выданный grant повторно валидируется перед использованием. Более мягкая policy не ретроактивно одобряет ожидающее действие без нового evaluation.

## Data retention

Полная история чата хранится бессрочно без автоматического удаления по возрасту. PlatformConfig задаёт retention служебных checkpoints/transport blobs, не удаляя историю или принятые вложения. Ручная очистка workspace затрагивает только выбранные файлы; правила временных загрузок определены в [Файлах](artifacts.md). Memory retention/delete выполняет подсистема памяти; Core обязан удалить свои cached excerpts и transcript-derived copies в той же публикации. Разрешены только агрегированные метрики и обязательные compliance tombstones.

## Keycloak и scope входящих запросов

Компания определяется только trusted `CORE_AGENT_TENANT_ID`. Стабильная identity
равна проверенной паре issuer + `sub`; credential string не является ключом
ownership. Runtime introspection использует только настроенный issuer endpoint
и confidential client, проверяет `active`, issuer, ожидаемый `aud`, непустой
`sub`, срок `exp` и требуемую роль. Роли принимаются из realm или client roles
ожидаемого audience, а не произвольного другого клиента. Owner-role default —
`agent-owner`, external-role default — `agent-external`; наличие external роли
запрещает owner/HITL authority даже при одновременно заявленной owner роли.
Introspection не кешируется между HTTP-запросами; её недоступность закрывает
доступ. Issuer URL требует HTTPS, loopback HTTP допускается только в explicit
development/test. Raw incoming credentials не сохраняются в durable records.
Transport/SDK MUST NOT заменить trusted tenant значением JSON-RPC metadata,
REST path или default пустой строкой: несовпадающий заявленный tenant
отклоняется, отсутствие/пустое значение сохраняет проверенный company scope.

### AUTH-02. Внешние агенты

- У каждого внешнего агента отдельная сервисная учётная запись в Keycloak.
- Входящий credential передаётся как `Authorization: Bearer <access_token>`.
- Выпуск, срок жизни, замена и отзыв credential относятся к Keycloak.
- Требуемый сценарий — однократно настроенный access token со сроком от месяца
  до года, если его раньше не отозвали. Параметры Keycloak и фактическая работа
  такого срока должны быть проверены при интеграции.
- Приложение не выпускает собственные API-ключи и не хранит входящие токены.
  Owner UI «Доступ к агенту» управляет сервисными клиентами и получает токены
  через Keycloak Admin API от имени текущей сессии владельца. Keycloak остаётся
  источником credentials, issuance metadata, срока и отзыва; дополнительная
  служебная учётка для provisioning не требуется.
- Каждый входящий запрос проверяется через Keycloak introspection, включая
  активность токена, назначение и необходимые права. При невозможности
  выполнить проверку доступ закрывается.
- Данные принадлежат стабильной идентичности сервисной учётной записи;
  замена токена не создаёт нового владельца существующих данных.
- Сервисная учётная запись внешнего агента не даёт прав владельца или HITL.

### AUTH-03. Изоляция внешних агентов

Внешний агент видит только свои чаты, задачи и файлы. Это правило действует для
создания сообщений, Get/List/Subscribe/Cancel, получения вложений и любых
дополнительных API. Знание чужого идентификатора не даёт доступа. Ответ не должен
раскрывать существование недоступного объекта.

Ограничение распространяется на доступ из Python, terminal, памяти, инструментов,
summary и retrieval. Владельцы видят все чаты в UI, но это не означает, что
выполняющаяся задача автоматически получает все файлы компании.

### AUTH-04. Уже открытые HTTP-потоки

Авторизация выполняется при приёме HTTP-запроса. В рамках уже авторизованного
долгого ответа, включая stream событий или скачивание файла, повторной
авторизации нет: не выполняются периодическая introspection или проверки
токена перед каждым кадром. Истечение токена после открытия само по себе
не закрывает этот ответ и не отменяет принятую задачу.

Каждый новый HTTP-запрос, в том числе переподключение к stream, отдельное
скачивание и решение HITL, снова проходит обычную проверку доступа.
Повторное использование TCP-соединения через keep-alive или HTTP/2
не переносит авторизацию одного запроса на другие. Изоляция ресурсов
и ограничения публичного содержимого продолжают действовать.

## Guardrails и решения по материалам

### GUARD-01. Проверка и решение владельца

Недоверенные сообщения, файлы, ответы инструментов и внешних агентов не могут
подменять системные правила и расширять доступ. Если механизм guardrails
считает содержание подозрительным, решение передаётся владельцам в том же чате.
Одобрение относится к использованию конкретного материала в текущих правах;
оно не отключает серверную policy или изоляцию данных.

Согласованный LLM-детектор и места проверки описаны в [LLM-детектору](security-and-reliability.md).
Нельзя обещать обнаружение всех prompt injections. Независимо от
детектора должны действовать серверная авторизация, tool policy, изоляция
и защита секретов.

### GUARD-02. Отказ владельца от использования материала

Если владелец отклонил подозрительное сообщение, файл или результат инструмента,
агент не использует этот материал. Основная модель получает структурированное
уведомление об отказе с идентификатором/типом источника, без самого содержимого
и без цитирования подозрительных инструкций. Для tool result уведомление
заменяет отклонённый результат, сохраняя связь с исходным tool call.

Задача автоматически не переходит в `failed`. Агент может продолжить по
оставшимся разрешённым данным, выбрать другой допустимый способ решения или
запросить недостающую информацию. Он не должен выдавать отклонённый материал
за проверенный результат или придумывать его содержание.

Решение связывается с конкретным материалом и его версией.
Ограничение действует и при последующих обращениях: материал не возвращается
модели через summary, memory, retrieval, повторное чтение файла или другой
инструмент. Для подозрительных файлов нужен карантин вне доступной Bubblewrap
папки; одного удаления текста из model context недостаточно. До разрешения
содержимое не должно поступать в основную модель или вызываемые ею инструменты.
Если материал сохраняется для истории/проверки владельцами, такое хранение
не делает его доступным agent loop; принятые материалы и owner history не относятся к временным неуспешным загрузкам и не удаляются их cleanup-ом.

### GUARD-03. Таймаут решения владельца

Срок ожидания решения guardrails настраивается; по умолчанию он составляет
24 часа с момента создания запроса владельцам. Абсолютный deadline сохраняется
в durable state и не начинается заново при restart, переподключении UI или
поступлении follow-up.

Если решение не получено вовремя, материал остаётся недоступным по правилам
GUARD-02. Основная модель получает уведомление «Срок ожидания решения по
материалу истёк; использовать материал нельзя» без его содержимого. В истории
фиксируется timeout, а не отказ, якобы сделанный владельцем.

Агент может продолжить задачу по разрешённым данным; автоматического перехода
в `failed` нет. Для tool result сохраняется связь с исходным tool call.
Следующий model call получает также накопленные follow-up по TASK-03.
Одновременное решение владельца и срабатывание deadline должны фиксировать
один исход запроса и приводить к одному продолжению.

### GUARD-04. Ошибка или недоступность детектора

Если требуемую проверку выполнить не удалось, материал не считается проверенным
или автоматически разрешённым. В соответствующем чате создаётся запрос
владельцам с пометкой «Не удалось проверить материал», без утверждения,
что prompt injection уже обнаружена. До решения содержимое закрыто от агента.

Разрешение владельца позволяет использовать конкретный материал в существующих
правах. Отказ обрабатывается по GUARD-02. Ожидание настраивается и по умолчанию
составляет 24 часа; timeout обрабатывается по GUARD-03. Недоступность детектора
сама по себе автоматически не переводит всю задачу в `failed`.
Если проверка материала явно исключена настройкой TOOL-02, детектор для этой
области не вызывается и его недоступность не создаёт запрос guardrails.

## Отдельный LLM-детектор


Для первой версии используется отдельный LLM-вызов классификации через
существующий model adapter. По умолчанию используется подключённая модель
агента; модель и её подключение для
guardrails должны настраиваться отдельно. Это отдельный короткий контекст без
tools, полномочий исполнения, секретов и истории других чатов. Обучение новой
модели, собственный inference server и новый pod для этого варианта не нужны.

Основание выбора — переиспользование текущей интеграции и универсальная политика
проверки без привязки к конкретной предметной области. По решению пользователя
оценка качества на наборе данных, benchmark и подбор модели по их результатам
не входят в объём работ и не являются условиями приёмки. Точность детектора
не измеряется; преимущество над другими моделями и полнота обнаружения атак
не заявляются.

Новый framework, собственный inference server и отдельный pod для детектора не требуются.

Порядок проверки:

1. Доверенный runtime определяет источник и конкретную версию материала.
   Детектор получает тип источника и минимальный относящийся к задаче контекст,
   чтобы различать пользовательское уточнение и инструкции из чужого документа.
2. Перед передачей основной модели проверяются новые входящие сообщения,
   извлечённое содержимое файлов и результаты tools/A2A; перед dispatch —
   аргументы вызова. Исключения TOOL-02 применяются к аргументам и результатам
   конкретного инструмента, но не отключают проверки входящих сообщений/файлов.
3. Отдельный запрос с фиксированной политикой ищет попытки подменить инструкции,
   изменить задачу через недоверенный источник или обойти права/изоляцию.
   Обычные просьбы написать код и цитирование примера атаки сами по себе
   не должны считаться основанием для блокировки.
4. Runtime валидирует структурированный ответ детектора. «Подозрение не найдено»
   позволяет продолжить обычные проверки; подозрение или неуверенный результат
   передаётся владельцу. Это не выдача инструменту разрешения на выполнение.
5. Пустой, повреждённый ответ, timeout API или неполная проверка обрабатываются
   по GUARD-04. Произвольный текст ответа классификатора не становится новой
   инструкцией основной модели.

Для длинных документов проверяется извлечённый текст по фрагментам с перекрытием
и учётом границ документа. Проверка только первых токенов, обрезание хвоста или
проверка одного summary не дают статуса «проверено» всему исходному материалу.
Если формат не поддерживается, извлечение неполно или исчерпаны лимиты времени
и токенов проверки, материал считается непроверенным и идёт к владельцу.
Приём файла до 25 МБ не означает, что все его байты помещаются в контекст LLM.

Для guardrails отдельно учитываются расходы и задержка. Их вызовы не являются
рассуждением основного агента, но требуют ограниченного бюджета; бесконечные
повторы проверки недопустимы. Ожидание владельца использует ранее согласованный
durable flow и 24-часовой настраиваемый timeout.

Детектор по умолчанию ограничен 60 секундами на материал, 100 000 входными
токенами суммарно с инструкциями и перекрытиями и 32 физическими запросами.
Deployment может изменить эти положительные пределы. Абсолютный deadline и
начисленные попытки сохраняются до сети; recovery не обнуляет их. Ошибка записи
attempt не допускает сетевой запрос. Нет автоматических retries. Исчерпание
любого предела, неполное извлечение или занятый недоступный detector дают
`unverified` и решение владельца. Поздний ответ после deadline не открывает
материал; количество оставшихся в работе запросов ограничено.

Принимается только объект JSON с единственным полем `verdict` со значением
`clear`, `suspicious` или `uncertain`; повторяющиеся ключи, tool calls,
незавершённый ответ и дополнительные поля недопустимы. Проверка всех фрагментов
даёт `clear` только при отдельных `clear` для каждого. В основной контекст
не передаётся свободный текст классификатора или текст его ошибок.

Для приёмки проверяется механика интеграции: отдельный контекст и настройка
модели, валидация ответа, обработка вердиктов/ошибок, исключения TOOL-02,
HITL, timeout и сохранение ограничений доступа. Эти проверки используют
заданные ответы детектора и не оценивают точность классификации реальных
или синтетических материалов. Runtime учёт расходов и задержки сохраняется;
это эксплуатационная наблюдаемость, а не benchmark качества.

### AUTH-04. Выдача внешнего доступа владельцем

Только authenticated company owner управляет внешним доступом. Его текущий
bearer передаётся только фиксированному Admin API настроенного Keycloak realm;
redirects, environment proxy и caller-selected issuer запрещены. Недостаточные
права Keycloak дают понятный 403, без fallback на bootstrap administrator.
Административные права владельцев Keycloak приняты как часть deployment policy.
Raw bearer, client secret, access/refresh token не сохраняются приложением,
не попадают в audit, telemetry, Tasks/model context или списки доступа.
Ответ выдачи имеет no-store; UI держит access token только в открытой модалке
и удаляет его из своего состояния при закрытии, переходе, выходе или unmount.
Гарантия не запрещает пользователю или браузеру самостоятельно сохранить копию.

Новая учётка получает только external authority для этого API, никогда owner/HITL.
Имя — непустой текст до 100 символов без control characters; срок — целое число
1–365 дней, default 30. Реальный issuer/audience/role/identity/expiry проверяется
перед выдачей; неподтверждённый длинный срок не считается успешной выдачей.
Для выдаваемых одноразово service tokens отключается native refresh-session
mode: срок доступа не должен зависеть от более короткого offline session idle.
Keycloak client attributes сохраняют tenant, audience, исходный request ID,
название, состояние операции, время выдачи и истечения, но не сам токен.
Повтор завершённого создания не показывает прежний токен и не создаёт дубликат;
незавершённое создание можно продолжить по тому же request ID с теми же данными.
Замена токена сохраняет client/service-account sub и отзывает прежние токены
через native client notBefore и service-user logout после перехода секунды.
User revocation сохраняется отдельно и закрывает realm/client notBefore
совместимость старых Keycloak; повторный токен проверяется introspection.
Отзыв отключает клиент без удаления его identity,
задач и файлов; новый HTTP-запрос отклоняется, уже открытый response не reauth-ится.
Отдельное действие «Удалить» после подтверждения необратимо удаляет native
Keycloak client вместе с service-account user. Удалять можно только внешнюю
учётку этого tenant/audience; учётки с owner authority исключены, включая
клиентов с issuance metadata. Задачи, файлы и принятая работа не удаляются
и не отменяются: владельцы сохраняют доступ. Новая учётка получает другой sub
и не наследует caller scope удалённой, даже если название совпадает.
Удаление не переавторизует уже открытый response; новые запросы старого токена
отклоняются. Сбои Keycloak не дают ложного подтверждения: UI перечитывает список,
а неизвестный исход не вызывает автоматическое повторение мутации.
Истечение токена не удаляет учётку. Existing manual external clients с нужным
API audience (включая default client scope) и external role в realm либо API
client видны с неизвестным сроком, если issuance metadata отсутствует.
Учётки с owner role в любом из этих двух scopes в этот список не входят.
