# Незакрытые задачи enterprise релиза

Состояние на 2 октября 2026 года, после объединения изменений в `main`
(`ce94087`). Документ фиксирует оставшуюся работу и проверки. Он не меняет
нормативную спецификацию и не разрешает редактировать замороженные spec/tests.

Основные enterprise доработки сохранены в репозитории. Открытая задача ниже
может означать отсутствие сквозного доказательства, необходимость аудита или
условную миграцию; это не утверждение, что соответствующий механизм отсутствует.
Источники: [план реализации](2026-09-29-enterprise-agent-implementation.md),
[матрица реализации](../../../spec/implementation-status.md) и
[профиль релиза](../../../spec/releases/v1.md).

## Проверки на целевом Kubernetes

- [ ] **1. Завершить проверку сетевой изоляции IPv4 и IPv6.**
  На целевом amd64 кластере выполнить существующие проверки с контролируемыми
  сетевыми получателями: доступ к публичному интернету, запрет внутренних,
  служебных и metadata адресов, обе версии IP и отказ запуска при невозможности
  установить сетевые ограничения. Сохранить digest образа, конфигурацию,
  результаты без пропусков и подтверждение очистки тестовых ресурсов.
  Основание: ENT-AC-33–36, [среда исполнения](../../../spec/execution-environment.md).
  Локальный native ARM64 прогон уже проходил; целевой прогон этих сетевых
  сценариев ещё не выполнен.

- [ ] **2. Проверить ограничение процессов на целевом кластере.**
  Подготовить безопасную изолированную fixture и выполнить bounded проверку
  действующего лимита и завершения дерева процессов. Существующий тест
  рассчитан на aggregate Pod limit 512. На целевом Pod подтверждён конечный
  лимит 9462, поэтому изменение kubelet до 512 само по себе не требуется.
  Нельзя считать тест на 513 попыток доказательством предела 9462 или заменять
  его неконтролируемым запуском тысяч процессов на общем узле.
  Основание: ENT-AC-30 и existing native Linux gate.

- [ ] **3. Проверить восстановление выполнения с постоянной папкой чата.**
  Сохранить файлы через реальные команды root, child и background execution,
  пересоздать Pod с тем же CSI томом и PostgreSQL, затем выполнить recovery
  и команды в том же чате. Проверить содержимое файлов и прежнюю привязку
  company/owner/context; соседние чаты должны оставаться недоступны.
  Основание: ENT-AC-32, [среда исполнения](../../../spec/execution-environment.md).
  Сохранность байтов и checksum на CSI после пересоздания Pod уже подтверждена,
  но сама по себе не доказывает сквозной runtime recovery.

Seccomp и AppArmor уже установлены на тестовом узле. Обход несовместимости
idmapped mount TUN через отдельный CSI том проверен; на целевом кластере
прошли 10 native sandbox tests. Повторная установка профилей не является
отдельной незакрытой задачей. Проверенные файлы и инструкции находятся в
[deploy/kubernetes/apparmor](../../../deploy/kubernetes/apparmor/README.md).

## Сквозной прогон с реальными моделями

- [ ] **4. Выполнить полный сценарий агента с Cloud.ru и памятью PostgreSQL.**
  Через обычный вход агента проверить реальные обращения к модели, вызовы
  инструментов памяти, запись и поиск документа, а затем чтение после
  перезапуска. Использовать фактическую размерность embeddings 1024 для
  `Qwen/Qwen3-Embedding-0.6B`. Сохранить результаты без credentials и содержимого
  секретных заголовков; проверить, что ожидаемые обращения к провайдерам
  действительно состоялись, а деградация памяти не была принята за успешный
  полный сценарий.
  Основание: [память](../../../spec/memory-service.md) и existing deployment
  obligations в основном плане. Actual embedding adapter и streaming model
  adapter уже отвечали успешно. Эта задача проверяет интеграцию; оценка качества
  универсального агента на отдельном наборе данных не входит в согласованный объём.

## Условная миграция старых Task и чатов

- [ ] **5. Закрыть вопрос старых данных перед переходом на новый runtime.**
  Установить, есть ли прежние Task, чаты и связанные файлы, которые должны
  оставаться доступны после перехода. Если есть, подготовить явное сопоставление
  company/owner/context и проверить перенос, доступ после перезапуска,
  отсутствие доступа чужих callers и согласованную границу rollback.
  Автоматически назначать владельца по недоверенным данным нельзя.
  Если таких данных нет, зафиксировать отсутствие необходимости именно в этом
  сопоставлении и проверить сценарий чистого запуска.
  Основание: ENT-MIG-01, [архитектура и миграции](../../../spec/architecture.md).
  Schema upgrade, повторный запуск migrations, восстановление DB/blob backup
  и отдельный импорт remote agent configuration уже проверены; импорт remote
  configuration не переносит ownership прежних Task и чатов.

Экспорт старых named artifacts из S3/MongoDB не требуется: пользователь
подтвердил удаление трёх инструментов и инфраструктуры, используемой только ими,
без сохранения прежних artifact данных. Эта работа не добавляется обратно в план.

## Аудит оставшихся пунктов матрицы реализации

- [ ] **6. Разобрать все foundation критерии со статусом partial.**
  Для каждого пункта сопоставить текущий end-to-end flow с уже существующими
  автоматическими проверками и найти конкретный непроверенный участок.
  Исправлять код только при подтверждённом несоответствии. Статус `partial`
  не является сам по себе доказательством дефекта или отсутствия реализации.

| Критерии | Что требуется подтвердить полностью |
|---|---|
| A2A-02–05 | Единый durable lifecycle, push/deduplication, follow-up на safe boundary и streaming после enterprise изменений. |
| CFG-02, CFG-03 | Отсутствие всех запрещённых capabilities в Card/model catalog и отказ stale dispatch; полный контракт разбора deployment settings. |
| BGT-02, SUB-01 | Освобождение worker при ожидании, recursive cancel, durable child identity и точные delegated capabilities. |
| TER-01, TER-02, PY-01 | Terminal/Python execution и broker после изменений workspace/sandbox; применимость прежнего snapshot/merge критерия к текущему release scope. |
| DB-02 | Company/tenant scope всех production rows, selectors и recovery, включая not-found для чужих идентификаторов. |
| SEC-01, SEC-02 | Безопасные публичные ошибки, redaction, trust boundaries, retention и очистка производных данных при удалении. |

В TER-02 осталось прежнее упоминание S3 manifest. Сначала нужно сверить его с
согласованным удалением artifact tools и действующим workspace контрактом.
Этот пункт не является поручением восстанавливать удалённую S3 инфраструктуру.
Если потребуется изменить нормативный критерий или frozen tests, получить
новую явную директиву пользователя до правок.

## Сверка доказательств и готовности релиза

- [ ] **7. Актуализировать матрицу после проверки доказательств.**
  Убрать устаревшее описание TUN mount как нерешённого препятствия, отразить
  уже выполненные целевые sandbox проверки и отделить их от оставшихся
  network/PID/CSI сценариев. Связать каждый criterion с проверкой обычного CI;
  ручной успешный прогон не заменяет необходимое автоматическое доказательство.
  После закрытия обязательств повторить применимые release gates и пересмотреть
  готовность релиза. Основные проверки и доказательства перечислены в
  [плане реализации](2026-09-29-enterprise-agent-implementation.md).

`spec/implementation-status.md` и `spec/releases/v1.md` заморожены. Создание
этого документа не разрешает менять их или tests. Для таких изменений требуется
новая явная директива пользователя и осознанное обновление hash lock.
До подтверждения всей совокупности обязательств профиль остаётся release candidate.
