# Публичные сообщения и явный выбор артефактов A2A

Статус: дизайн согласован; пользователь одобрил изменения нормативной
спецификации, tests и hash lock. Выбран режим немедленной публикации Artifacts.

## Требуемое поведение

Агент самостоятельно определяет, нужен ли отдельный артефакт для результата
работы. Обычные промежуточные сообщения и финальный ответ передаются через
Message. Бэкенд не создаёт Artifact из текста ответа автоматически.

Пример: ответ на поручение узнать погоду передаётся текстом Message. Если агент
дополнительно решает предоставить прогноз в JSON или подготовленный отчёт,
он явно выбирает соответствующие артефакты. Текстовый Artifact также допустим,
но требует такого же явного выбора.

## Контракт передачи

- Task сохраняет существующий lifecycle, идентификаторы, авторизацию и scope.
- Финальный публичный ответ становится agent Message в `Task.status.message`.
  Сообщение со стабильным server-owned ID сохраняется durable до публикации
  `completed`; оно доступно через GetTask, поток и push после восстановления.
- `historyLength=0` не удаляет финальный `status.message`. Промежуточные публичные
  сообщения сохраняются в истории; потоковые снимки незаконченного текста
  остаются preview и не дублируются в истории как отдельные реплики.
- Коллекция `Task.artifacts` содержит только явно выбранные моделью артефакты.
  Без выбора коллекция пуста; финальный ответ при этом остаётся доступен.
- Hidden reasoning, внутренние tool calls и переписка с владельцами не
  становятся публичными сообщениями или артефактами.

[A2A 1.0 §3.7](https://a2a-protocol.org/v1.0.0/specification/#37-messages-and-artifacts)
рекомендует публиковать результаты задач как Artifacts. Финальный результат
через Message является осознанным отклонением от этой рекомендации. Гарантию
durable доставки Message нужно явно описать в контракте интеграции: сторонний
клиент, читающий только Artifacts, не получит текстовый ответ.

## Выбор артефактов

Предлагается расширить существующий механизм выбора файлов ответа инструментом
`core_response_artifacts`. Он принимает именованные артефакты с упорядоченными
Parts трёх видов: текст с media type, структурированные JSON-данные и
относительный путь к файлу текущего workspace. Изображения, документы, архивы
и другие бинарные форматы передаются файловыми Parts с соответствующим media type.

Чтение файлов, immutable snapshots, проверка целостности и scoped storage
переиспользуют `ResponseFileService`; новая S3/Mongo инфраструктура не требуется.
Идентификаторы артефактов выдаёт бэкенд. Повторное исполнение сохранённого вызова
не создаёт дубликатов. Текст, JSON и файлы учитываются в общем лимите артефактов.
Сохраняются схема аргументов, policy/HITL, guardrails, audit и бюджеты запуска.

Артефакты публикуются сразу после явного прикрепления. Агент может отдать готовый
результат и продолжить работу; опубликованный batch immutable и append-only,
без replace/remove/clear. Receiver принимает full early Artifact только с
`metadata.core_agent_artifact: {version: 1, complete: true, immutable: true}`;
quarantine, reviews и scoped publication предшествуют доступности content.
Generic third-party результаты без этого marker сохраняют terminal fallback.
V2 `core_response_files` остаётся file-only compatibility alias: непустой paths
немедленно добавляет один Artifact, `[]` — no-op; legacy принятые runs сохраняют
прежний replace/clear selection-at-final контракт.

## Приём результатов

Текст Messages передаётся модели после действующих проверок материала.
Реальные входящие Artifacts сохраняются в `workspace/a2a/<operation-id>/`
по существующим правилам; модель получает manifest и пути. Артефакты сторонних
агентов не превращаются автоматически в Messages, включая текстовые.

Одна общая проекция результата обслуживает live execution, recovery, GetTask,
streaming и push. UI показывает сообщения как переписку и выбранные артефакты
как отдельные результаты. Дедупликация использует стабильные ID.

## Уточняющие вопросы

Тип Message сам по себе не означает ожидание ответа. Промежуточное сообщение
оставляет Task в `working`; обычный финальный ответ завершает Task.
Для публичного вопроса вызывающему агенту требуется отдельное явное действие
с переходом в `input-required`. Такого действия у нашего отправителя сейчас нет;
его добавление нужно согласовать отдельно. `core_ask_owner` остаётся приватным
вопросом владельцам и не даёт внешним агентам прав отвечать за владельца.

## Совместимость и изменение реализации

Новый output contract фиксируется при создании нового запуска. Уже принятые
задачи, их артефакты и результаты продолжают читаться по прежнему контракту;
перезапуск не переформатирует сохранённые ответы.

Изменение затрагивает схемы инструментов и инструкции модели, runtime selection,
immutable output snapshots, A2A adapter и canonical Task projection, проекции
push/recovery, приём remote results и отображение UI. Требования и связанные
проверки должны обновляться вместе; hash lock не ослабляется.

Критерии проверки: текстовый ответ без выбранных артефактов доступен как Message;
явно выбранные text/data/file Parts сохраняют тип, порядок и содержимое;
обрыв и перезапуск не теряют сообщения и не дублируют артефакты; scoped access,
guardrails/HITL и суммарный лимит сохраняются; старые результаты читаются без
преобразования. Для первого режима также проверяется выдача готового артефакта
в работающей Task.
