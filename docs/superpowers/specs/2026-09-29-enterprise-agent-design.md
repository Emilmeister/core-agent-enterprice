# Доработки Core Agent: рабочее ТЗ

Дата: 29 сентября 2026 года. Статус: **DRAFT — для согласования**.

Документ собирает решения из обсуждения и результаты анализа текущего кода.
Разделы 2–11 и 12.1–12.3 описывают согласованное направление; явно обозначенные
предложения и вопросы ещё требуют решения. Критерии приёмки ниже — текстовые сценарии,
а не реализованные или пройденные автоматические проверки.

Этот черновик не заменяет нормативный `spec/` и не разрешает изменение
замороженных `spec/**/*.md`, `tests/**` и hash lock. Перед реализацией потребуется
явная директива на соответствующие правки согласно `AGENTS.md`, затем перенос
согласованных требований в нормативные документы.

## 1. Цель и исходное состояние

Агент принадлежит компании. Несколько владельцев совместно используют UI,
управляют инструментами и доверенными внешними агентами, отвечают на вопросы
и принимают решения HITL. Агент обслуживает долгие задачи через чат и A2A,
сохраняя работу при ожиданиях и перезапусках.

Текущий путь выполнения: A2A transport → создание workflow и durable inbox →
agent loop → проверка и dispatch инструмента → результат/события workflow →
A2A Task и поток обновлений. Обработчик сообщений с существующим `taskId`
сохраняет follow-up; runtime доставляет его на безопасной границе.

| Область | Наблюдение в текущем коде | Требуемая доработка |
| --- | --- | --- |
| UI и Keycloak | Готовый UI не найден; Keycloak не подключён в composition root | UI, аутентификация и авторизация всех новых границ |
| HITL | Есть элементы workflow для approval, но нет подключённого operator flow | Сквозное ожидание, решение владельца, timeout и recovery |
| A2A follow-up | Приём в SDK adapter и durable доставка в runtime уже существуют | Сохранить механизм и согласовать его с новыми ожиданиями |
| Занятость чата | Нет общей проверки одного активного корневого задания на context | Атомарное ограничение при создании задачи |
| Исходящий A2A | Текущий вызов синхронный; используются идентификаторы корневого запуска | Независимые remote IDs, durable ожидание и восстановление |
| Ожидание задач | `core_task_wait` сейчас удерживает выполняющий поток | Ожидание с освобождением worker и сохранением продолжения |
| Файлы | Входящие бинарные вложения могут сохраняться через artifact service | Сохранение в папку чата и двусторонняя передача через A2A |
| Workspace | Папки принадлежат run; Python/terminal работают внутри общего контейнера | Постоянная папка чата и реальное ограничение доступа |
| Суммаризация | `StructuredSummarizer` формирует текст и обрезает сериализованную историю | Семантическая суммаризация и перенос контекста между задачами |
| История чата | Новый workflow начинает контекст с нового prompt | Подключение истории/summary того же чата |
| Cron | Готовая подсистема в исследованном runtime не обнаружена | Управление расписаниями, запуски и защита от перекрытия |

Точки реализации: `core_agent/app.py`, `a2a_sdk.py`, `runtime.py`, `workflow.py`,
`database.py`, `tools.py`, `config.py`, `context.py`, `remote_agents.py`,
`execution.py`, `python_exec.py`, `artifact_service.py` и `artifacts.py`.
Наличие target capability в существующем `spec/` не доказывает её реализацию.

## 2. Владение, Keycloak и права доступа

### AUTH-01. Владельцы

- Агент принадлежит одной компании; владельцев может быть несколько.
- Владельцем считается пользователь со специальной ролью в Keycloak.
- Владельцы имеют общий доступ ко всем чатам, задачам, файлам и настройкам агента.
- Только владельцы используют UI, изменяют настройки и принимают HITL.
- Приложение проверяет права на сервере. Скрытая кнопка в UI не заменяет проверку.

### AUTH-02. Внешние агенты

- У каждого внешнего агента отдельная сервисная учётная запись в Keycloak.
- Входящий credential передаётся как `Authorization: Bearer <access_token>`.
- Выпуск, срок жизни, замена и отзыв credential относятся к Keycloak.
- Требуемый сценарий — однократно настроенный access token со сроком от месяца
  до года, если его раньше не отозвали. Параметры Keycloak и фактическая работа
  такого срока должны быть проверены при интеграции.
- Приложение не выпускает собственные API-ключи, не ведёт их реестр и не
  предоставляет UI для их выпуска, продления или отзыва.
- Каждый входящий запрос проверяется через Keycloak introspection, включая
  активность токена, назначение и необходимые права. При невозможности
  выполнить проверку доступ закрывается.
- Данные принадлежат стабильной идентичности сервисной учётной записи;
  замена токена не создаёт нового владельца существующих данных.
- Сервисная учётная запись внешнего агента не даёт прав владельца или HITL.

### AUTH-03. Изоляция внешних агентов

Внешний агент видит только свои чаты, задачи и файлы. Это правило действует для
создания сообщений, Get/List/Subscribe/Cancel, получения вложений и любых
дополнительных API. Знание чужого идентификатора не даёт доступа. Ответ не должен
раскрывать существование недоступного объекта.

Ограничение распространяется на доступ из Python, terminal, памяти, инструментов,
summary и retrieval. Владельцы видят все чаты в UI, но это не означает, что
выполняющаяся задача автоматически получает все файлы компании.

## 3. UI и границы API

### UI-01. Чаты

- Вход владельца через Keycloak.
- Общий список чатов, история сообщений, задачи и их состояния.
- Отправка текста и файлов, получение и скачивание файлов агента.
- Просмотр файлов workspace и ручная очистка с предварительным списком
  удаляемых файлов по FILE-04.
- Прогресс, ожидания, ошибки, итоговые ответы и переподключение к активной задаче.
- Запросы HITL и вопросы владельцу отображаются внутри соответствующего чата.
- Отдельный общий список HITL не требуется.
- Для входящего внешнего A2A один `contextId` соответствует одному чату.
- Для каждого расписания cron используется свой постоянный чат.

### UI-02. Настройки

В UI владельцы управляют политикой каждого инструмента, исключением инструмента
из проверки guardrails, доверенными внешними агентами и расписаниями cron.
Предусмотреть настройку согласованных таймаутов
и лимита вложений; точное распределение между UI и deployment env — вопрос Q8.
Корень папок чатов обязательно задаётся через env.

### API-01. Разделение входов

- Отдельный A2A endpoint для владельцев.
- Отдельный A2A endpoint для внешних агентов.
- Отдельный авторизованный endpoint решений HITL, доступный только владельцам.
- Конкретные URL и schemas предстоит определить в нормативном API-контракте.
- Tenant/identity/права выводятся из проверенного transport context, а не из
  текста сообщения, поля metadata или аргументов инструмента.

### A2A-01. Два направления общения

1. Наш агент вызывает через инструмент A2A endpoint доверенного внешнего агента.
   Список доверенных агентов и параметры подключения настраиваются владельцами
   в UI. В частности, настраиваются имя и значение заголовка авторизации;
   исходный вариант — `Authorization: Bearer ...`.
2. Внешний агент вызывает наш внешний A2A endpoint со своим Keycloak credential.

UI показывает эти обмены в контексте работы нашего агента. Прямой чат владельца
с внешним агентом в обход нашего агента не входит в согласованный объём.
Значения исходящих секретных заголовков не передаются модели и не публикуются
в сообщениях, логах и traces. Это конфигурация подключения, а не выпуск ключей.
Автоматическое получение исходящего OAuth token — отдельный вопрос Q7.

## 4. Задачи в чате и follow-up

### TASK-01. Одна активная корневая задача

В одном чате одновременно выполняется не более одной корневой задачи.
Ожидание HITL, ответа владельца, внешнего агента или времени пробуждения
сохраняет занятость чата. Разные чаты могут выполняться независимо.
Внутренние дочерние задачи и делегирование принадлежат корневой задаче;
это ограничение не запрещает их разрешённый параллелизм.

### TASK-02. Новая задача при занятом чате

Сообщение в существующий `contextId` без `taskId` трактуется нашим контрактом
как запрос новой задачи. Если чат занят:

- сохраняется отдельная запись новой A2A Task с собственным `taskId`;
- она сразу имеет терминальное состояние `failed` (`TASK_STATE_FAILED` в A2A 1.0);
- причина — наш машинный признак `CONTEXT_BUSY`, понятное пояснение и
  `activeTaskId` текущей доступной вызывающему задачи;
- выполнение новой задачи не начинается, очередь не создаётся;
- текущая задача продолжает работу;
- ответ является объектом неуспешной Task, а не одновременно JSON-RPC error;
- GetTask возвращает тот же сохранённый результат попытки.

Проверка занятости и регистрация успешного старта должны быть атомарными:
два одновременных запроса не могут запустить две корневые задачи одного чата.
Завершившаяся запись `failed` сама не занимает чат.

### TASK-03. Сообщение в активную задачу

- Сообщение с `taskId` существующей нетерминальной задачи является follow-up.
- Оно сохраняется durable при приёме; текущий tool call не прерывается.
- После результата текущего инструмента сообщение добавляется в контекст
  перед следующим обращением к модели.
- Если инструмент сейчас не выполняется, доставка происходит на ближайшей
  безопасной границе agent loop.
- Порядок сообщений сохраняется; повтор одного `messageId` в задаче не создаёт
  повторного user turn.
- Принятое сообщение не теряется при гонке с завершением и при перезапуске.
- Follow-up не является решением HITL и не повышает права вызывающего.
- Для терминальной задачи требуется новый Task в том же чате.

Если задача ожидает HITL или ответ внешнего агента, follow-up сохраняется
сразу, а модели передаётся после завершения ожидания, перед следующим
обращением к ней. Уточнение само не завершает ожидание, не заменяет решение
HITL и не продлевает deadline. Это правило согласовано отдельно.
Применение того же правила к ожиданию времени пробуждения пока предложено,
но отдельно не согласовано.
Порядок при пакете нескольких tool calls должен сохранять корректные пары
вызов/результат для model API; эта деталь требует уточнения реализации.

## 5. Политики инструментов и HITL

### TOOL-01. Три режима для каждого инструмента

| Режим | Каталог модели | Вызов |
| --- | --- | --- |
| Разрешён | Инструмент виден | Выполнение после остальных проверок |
| Требует HITL | Инструмент виден | Каждый конкретный вызов ожидает решение владельца |
| Запрещён | Инструмент отсутствует | Сервер также отклоняет попытку вызова |

Политика применяется к built-ins и MCP. Новый инструмент по умолчанию требует
HITL. Верхние ограничения platform/tenant и текущего runtime mode сохраняются:
UI не разрешает возможность, запрещённую более строгим ограничением.

Все пути выполнения, включая `tools.call(...)` из Python и делегирование,
проходят одинаковую серверную проверку. Policy и каталог заново учитывают
изменения владельца для последующих вызовов уже активной задачи. Начатый вызов
означает уже переданный на исполнение вызов; он не прерывается из-за изменения
настройки. Ожидание HITL сохраняется при переходе в автоматический режим
по HITL-03 и сразу завершается при запрете инструмента по HITL-04.

### TOOL-02. Исключение доверенного инструмента из guardrails

Для каждого built-in и MCP tool владелец может через UI указать, что инструмент
доверенный и для него не нужна проверка guardrails. Это отдельная настройка от
трёх режимов TOOL-01: сама метка не разрешает запрещённый инструмент и не
заменяет решение HITL. Новый инструмент по умолчанию проверяется guardrails;
исключение включает только владелец.

Метка отключает guardrails и для аргументов вызова, и для результатов конкретного
инструмента: они не отправляются детектору и не создают связанных запросов
guardrails. Валидация аргументов по схеме, проверки прав, изоляция и лимиты
сохраняются в любом случае. Исключение не отключает отдельные проверки входящих
сообщений и файлов только потому, что они могут использоваться этим инструментом.
Ответ инструмента не становится системной инструкцией и не повышает права
агента из-за этой настройки.
Метка не отменяет уже зафиксированный отказ или timeout по конкретному материалу.

Модель, внешний caller и metadata самого MCP tool не могут установить эту метку.
Применение исключения связывается с идентичностью конкретного инструмента и
доверенной конфигурацией, а не с текстом его ответа. Исключение внешнего вызова
не отключает независимые проверки вложенных `tools.call(...)`.

### HITL-01. Запрос и решение

- Запрос связан с чатом, задачей и конкретным вызовом с конкретными аргументами.
- Владелец видит, какое действие и с какими аргументами запрашивается.
- Доступны только «Разрешить» и «Отклонить»; редактирования аргументов нет.
- Решение передаётся через отдельный endpoint с повторной проверкой роли.
- Внешние агенты не могут принимать решения даже по собственным задачам.
- До разрешения защищаемый вызов не выполняется.
- Решение и продолжение сохраняются durable; браузер не обязан оставаться открыт.

### HITL-02. Отказ и timeout

- Отказ возвращается модели как результат вызова инструмента.
- Агент может продолжить решение в рамках разрешённых возможностей.
- Таймаут настраивается, значение по умолчанию — 24 часа.
- По timeout возвращается результат «подтверждение не получено вовремя»;
  вся задача автоматически не завершается.
- Абсолютный срок сохраняется и не начинается заново после restart.

Инженерное предложение: первое зафиксированное решение либо timeout закрывает
запрос; повторная доставка решения идемпотентна. Одобрение и последующий dispatch
должны повторно проверять актуальную policy.

### HITL-03. Переход инструмента в автоматический режим

Если вызов уже ожидает HITL, перевод инструмента в автоматический режим
не разрешает этот вызов автоматически и не закрывает запрос владельцам.
Сохраняются исходные аргументы и прежний deadline. Вызов продолжает ждать
явного решения владельца либо завершается по прежнему правилу timeout.

Новые вызовы после изменения настройки используют автоматический режим,
в том числе в уже активных задачах других чатов. Настройка не отменяет
schema validation, остальные ограничения policy или проверки guardrails.

Перед исполнением ранее ожидавшего вызова после разрешения владельцем
повторно проверяются текущие ограничения: сохранённый HITL-запрос не позволяет
выполнить инструмент, который к этому моменту запрещён.

### HITL-04. Запрет инструмента во время ожидания

При переводе инструмента в запрещённый режим все ожидающие HITL вызовы этого
инструмента во всех чатах сразу завершаются без исполнения. Модель получает
структурированный результат «инструмент запрещён» и может продолжить задачу
с доступными возможностями. Это отказ policy, а не решение владельца
«Отклонить» по конкретному HITL-запросу; сам запрет не переводит задачу в failed.

Закрытие запроса и повод продолжения сохраняются durable. Позднее разрешение,
timeout или restart не открывают закрытый запрос и не запускают продолжение
повторно. Последующее включение инструмента действует для новых вызовов
и не восстанавливает закрытые. При гонке запрета с разрешением перед dispatch
проверяется актуальная policy; уже переданный на исполнение вызов подчиняется
правилу TOOL-01.

### INPUT-01. Вопрос владельцу

Агент может обратиться к владельцам за недостающей информацией и при работе над
задачей внешнего агента. Вопрос и ответ относятся к соответствующему чату;
внешний caller не получает прав владельца. Вопрос со свободным текстовым ответом
отличается от HITL, где доступны только разрешение и отказ.

При обращении к владельцам внешний агент видит только факт ожидания, например
«Ожидается ответ владельца», а после выполнения — итоговый ответ по задаче.
Тексты вопросов и ответов владельцев остаются во внутренней переписке, доступной
владельцам. Внешний caller не может ответить от имени владельца; его обычный
follow-up не закрывает ожидание ответа владельца.

Ограничение действует для всех внешних представлений этой Task: истории,
GetTask/ListTasks, потоковых событий, push-уведомлений, файлов, артефактов и
metadata. Нельзя раскрывать внутреннюю переписку через другой A2A-метод или
публикацию внутреннего transcript/summary. Агент использует полученные сведения
для решения задачи и формирования предназначенного внешнему caller-у итогового
ответа; саму переписку с владельцами автоматически в ответ не копирует.
Это правило дополняет изоляцию внешних агентов и действует даже внутри задачи,
принадлежащей данному caller-у.

Ожидание ответа владельцев имеет настраиваемый timeout, по умолчанию 24 часа.
Абсолютный срок сохраняется вместе с запросом и не начинается заново после
перезапуска или поступления follow-up. По истечении срока ожидание завершается,
а агент получает структурированный результат «ответ не получен вовремя» и может
продолжить задачу без этих сведений. Сам timeout не переводит задачу в failed;
агент не должен подменять отсутствующий ответ вымышленными данными.

Ответ владельца и истечение срока конкурируют за одно завершение ожидания:
возобновление происходит однократно. Сохранённые за время ожидания follow-up
доставляются перед следующим обращением к модели по общим правилам.
Конкретный API/tool запроса информации остаётся открытым в Q5.

## 6. Файлы и папки чатов

### FILE-01. Workspace

- Согласованная среда развёртывания — один Kubernetes Pod; все чаты
  обрабатываются в этом pod. Отдельные pod на чат не предполагаются.
- Python, terminal и фоновые команды изолируются через Bubblewrap по §12.1.
- При создании чата ему назначается отдельная постоянная папка.
- Задачи этого чата работают с одной папкой, в том числе повторные cron-запуски.
- Родительская папка задаётся переменной окружения.
- Файлы сохраняются при restart сервиса.
- Внешний агент и выполняемый по его запросу код не имеют доступа к соседним
  чатам и их файлам.

Текущее `LOCAL_WORKSPACE_ROOT` имеет семантику ephemeral workspace для run.
Предложение: отдельный `CHAT_WORKSPACE_ROOT` для постоянных папок чатов,
с сохранением существующих временных рабочих областей там, где они нужны.
Окончательное имя переменной определяется вместе с Q8. Bubblewrap предоставляет
процессу папку текущего чата как `/workspace`; смысл существующей переменной
нельзя менять молча.

### FILE-02. Приём вложений

- UI и A2A принимают файлы и сохраняют их в папке нужного чата.
- Подозрительный файл до решения guardrails изолируется от исполняющей среды;
  при отказе его содержимое не становится доступным агенту по GUARD-02.
- Лимит применяется к сумме размеров вложений одного сообщения.
- Значение по умолчанию — 25 МБ; лимит настраивается.
- Точное количество байтов для «МБ» следует закрепить по Q8.
- Для base64 сравнивается размер декодированных файлов; transport/proxy лимиты
  должны учитывать размер кодирования и остального сообщения.
- В контекст передаются фактические безопасные имена и путь к папке:
  «Прикреплённые файлы: …; папка: …». Данные файлов не подставляются целиком
  в system prompt.
- Содержимое, исходные имена файлов и сообщения внешнего агента недоверенные;
  их нельзя интерпретировать как privileged instructions.

Пути должны исключать выход из папки и переход по ссылке к чужим данным.
При совпадении безопасного имени с существующим файлом сохраняются оба:
новое вложение получает свободное имя с суффиксом перед расширением,
например `report_2.pdf`, затем `report_3.pdf`. Существующий файл не заменяется.
Правило одинаково для UI и A2A, включая одинаковые имена в одном сообщении
и конкурентные загрузки. Выбор свободного имени и сохранение исключают
перезапись при гонке; совпадение с каталогом или ссылкой также не даёт права
перезаписать существующий объект или перейти по ссылке.

UI и результат приёма A2A-вложения отражают фактическое сохранённое имя;
агент получает это же имя и доступный ему путь в сообщении о вложениях.

Сообщение с вложениями принимается целиком. Ошибка загрузки, декодирования
или сохранения хотя бы одного файла либо превышение суммарного лимита
отклоняет всё сообщение. Ни текст, ни успешно загруженная часть вложений
не передаются агенту; новое выполнение по этому сообщению не начинается,
follow-up не доставляется в активную задачу. Уже работающая задача продолжает
выполнение без отклонённого сообщения. UI или A2A caller получает явный отказ
с причиной, позволяющей исправить запрос и повторить отправку.

До готовности полного набора файлы находятся во временной области, недоступной
агенту. При отказе новые файлы этого сообщения не публикуются в workspace;
уже существующие данные сохраняются. Неуспешная загрузка и её временные файлы
не должны становиться принятыми после restart. Очистка временных данных
восстанавливается после сбоя; конкретный срок их хранения определяется в Q8.

Это правило описывает технический приём сообщения. Последующее решение
guardrails по уже принятому материалу обрабатывается по GUARD-01–04:
отказ владельца исключает материал и позволяет продолжить задачу без него.

### FILE-03. Выдача и отправка

- Агент может передать результирующие файлы владельцу через UI.
- В обоих направлениях A2A файлы передаются средствами A2A, а не путём
  предоставления доступа к общему workspace сервера.
- Выдача каждого файла проверяет scope вызывающего.
- Конкретный способ A2A file parts и применение лимита к исходящему сообщению
  нужно закрепить в API-контракте; ссылка не должна открывать чужие данные.

### FILE-04. Очистка workspace через UI

Владелец может удалить старые файлы из workspace выбранного чата через UI.
До удаления отображается список файлов: имя, относительный путь, размер
и дата последнего изменения. Владелец отмечает файлы и перед подтверждением
видит точный перечень выбранного, количество и суммарный размер.
Просмотр списка сам по себе ничего не удаляет.

В UI доступен фильтр «не изменялись более N дней»: владелец задаёт N,
а список отбирается по времени последнего изменения файла. Возраст считается
от серверного времени формирования списка; день означает 24 часа. Файл
на точной границе N дней ещё не соответствует условию «более N дней».
Из найденного списка владелец вручную отмечает файлы для удаления;
по умолчанию ничего не выбрано. Фильтр не запускает автоматическую очистку.

Подтверждение относится только к показанному и выбранному перечню. Файлы,
появившиеся позднее, не попадают в удаление автоматически. Если выбранный файл
после просмотра изменился или был заменён, он пропускается с пояснением
и требует обновления списка перед новым решением владельца.
Сервер повторно проверяет роль владельца и принадлежность путей выбранному
workspace; выход за его границы, в том числе через символические ссылки,
не допускается.

После операции UI показывает, какие файлы удалены, какие пропущены и какие
не удалось удалить, с причиной для каждого неуспешного результата. Ошибка
части операции не должна отображаться как удаление всего выбранного.
Очистка файлов сохраняет сам чат, историю и записи задач; перезапуск
не должен возвращать удалённые файлы в workspace из старого снимка.

Пока в чате есть активная задача, просмотр и фильтрация файлов доступны,
а удаление через очистку workspace заблокировано. Это относится и к ожиданию
HITL, ответа владельца, внешнего агента или времени пробуждения. UI показывает
причину блокировки, сервер повторно проверяет состояние перед удалением.
Заблокированная очистка не ставится в очередь: после завершения задачи
владелец может повторить её вручную.

Проверка занятости и очистка согласованы с приёмом новых задач, включая cron:
конкурентный запуск не может привести к удалению файлов во время активной
задачи. Эти операции не должны пересекаться даже при устаревшем состоянии UI.

## 7. Долгоживущие операции

### LONG-01. Отправка внешней задачи и ожидание

- Отправка задачи внешнему агенту может вернуть идентификаторы и позволить
  нашему агенту продолжить независимую работу.
- Ожидание сохраняет состояние и освобождает worker, не держит активный model call.
- Во время ожидания не расходуется бюджет model turns/tool calls на polling.
- Родительская A2A Task остаётся нетерминальной, при ожидании внешнего агента —
  `working`.
- Ожидание переживает закрытие UI/stream и перезапуск сервиса.
- Удалённое ожидание чужого HITL не означает завершения задачи. Решение там
  принимает владелец удалённого агента; наш агент ожидает дальнейшего результата.
- Закрытие SSE stream само по себе не означает успех или провал удалённой задачи.
- Сохраняется соответствие локального handle удалённым `taskId` и `contextId`.
  Идентификаторы корневой задачи нельзя подставлять вместо remote IDs.

Предложение: расширить существующие `core_agent_send_message` и task lifecycle
вместо введения второго независимого набора сущностей. Предусмотреть polling
через GetTask, например каждые 5 минут с настройкой интервала; SSE/push могут
ускорять обнаружение результата. Эти значения и имена инструментов пока
не являются окончательным публичным контрактом.

### LONG-02. Окончательный timeout операции

- Для ожидания задаётся предельный срок; его истечение окончательно закрывает
  возможность дальнейшего ожидания той же удалённой операции.
- Повторный wait немедленно возвращает, что эту операцию уже ожидали и срок истёк.
- В результате сообщается, что можно попробовать создать новую задачу.
- Не утверждается, что удалённая задача точно не завершилась: её исход может
  быть неизвестен, а побочный эффект уже выполнен.
- Deadline не продлевается повторным wait, follow-up или restart.
- По достижении deadline harness прекращает polling этой операции: новые
  GetTask и повторные подключения для получения результата не отправляются,
  запланированные проверки больше не исполняются, в том числе после restart.
  Перед каждым сетевым запросом проверяется актуальность ожидания и его срока.
- Если для ожидания используется SSE, локальная подписка закрывается и не
  восстанавливается. Дальнейший сбор результата и его публикация в чате
  с пометкой «получен поздно» не требуются.
- Ответ на запрос, отправленный до deadline, либо уже летящее SSE/push-событие
  всё же может прийти после timeout. Если timeout уже зафиксирован, такой
  результат игнорируется: он не меняет исход ожидания, не передаётся модели
  или в чат и не запускает продолжение заново.
- По timeout не отправляется автоматический CancelTask внешнему агенту.
- Новая удалённая задача создаётся отдельным действием; автоматическая повторная
  отправка после неоднозначного результата запрещена существующими гарантиями.

Пример результата: «Мы уже ожидали эту задачу, срок истёк. Повторное ожидание
недоступно; можно создать новую задачу. Исход предыдущей неизвестен».
Предлагаемый default — 24 часа с настройкой; это отдельный параметр от HITL.

### LONG-03. Ожидание времени

Нужен инструмент ожидания до заданного момента времени с сохранением продолжения
и восстановлением после restart. Пробуждение позволяет проверить внешнее событие,
например доставку; само время пробуждения не доказывает, что событие произошло.

### LONG-04. Надёжность продолжения

Инженерные требования к реализации: устойчивый workflow checkpoint, абсолютные
deadline, сохранённый повод ожидания и атомарный выбор исхода при гонке события
с timeout. Повторное уведомление не запускает продолжение дважды. Локальная
дедупликация не означает exactly-once гарантию внешнего побочного эффекта.

## 8. Cron

### CRON-01. Создание и выполнение

- Владелец создаёт расписания в UI.
- Агент может создавать их отдельным инструментом с общей политикой tools.
- Этот инструмент можно запретить и убрать из каталога модели; управление через
  UI при этом остаётся доступным владельцам.
- Новый инструмент по умолчанию требует HITL.
- Каждый запуск создаёт новую полноценную задачу с сохранённым prompt.
- Это не непосредственный запуск произвольной shell-команды по расписанию.
- Все запуски одного расписания используют один чат и его папку.

### CRON-02. Перекрытие запусков

Если предыдущий запуск ещё активен, включая ожидание HITL или внешнего агента,
новый запуск пропускается. Он не ставится в очередь и не запускается параллельно.
В чате записывается факт и причина пропуска.

Это отдельное правило scheduler-а: пропущенный cron tick не обязан создавать
`failed` Task. `TASK-02` описывает ответ на входящую попытку создать новую задачу.
Ручной запуск описан в CRON-06.

### CRON-03. Пропуски во время недоступности сервиса

Если сервис был недоступен в запланированный момент, пропущенный запуск
не выполняется задним числом. После восстановления scheduler ждёт ближайшего
будущего момента по расписанию: не создаёт очередь пропущенных запусков
и не запускает одну компенсирующую задачу сразу после восстановления.
В чате расписания фиксируются пропуск и его причина.

Это правило относится к новым запускам, которые не были приняты до сбоя.
Уже принятая и сохранённая задача восстанавливается по общим правилам workflow;
restart не превращает её в пропущенный cron tick. Если она ещё активна
к следующему моменту расписания, применяется CRON-02.

### CRON-04. Отключение и удаление расписания

Отключение или удаление расписания прекращает только будущие запуски.
Уже принятая задача продолжает работу, включая ожидание HITL, ответа владельца
или внешнего агента, и сохраняет возможность восстановления после restart.
Для её остановки владелец отдельно отменяет саму задачу.

Чат, история, файлы и ожидающие решения не удаляются вместе с расписанием.
При гонке scheduler-а с отключением или удалением атомарно определяется,
был ли новый запуск уже принят: принятый продолжает работу, после вступления
отключения или удаления в силу новые задачи по расписанию не создаются.

### CRON-05. Часовой пояс расписания

Для каждого расписания владелец выбирает часовой пояс в UI. Значение
по умолчанию при создании — `Europe/Moscow`; тот же default применяется
при создании через инструмент агента, если пояс явно не указан.
Часовой пояс сохраняется вместе с расписанием как идентификатор IANA,
а не только фиксированное смещение UTC. Некорректное значение отклоняется
при сохранении без молчаливой подстановки другого пояса.

Расписание вычисляется в сохранённом часовом поясе. Перезапуск, часовой пояс
pod или браузера владельца не меняют моменты запусков. UI явно показывает
выбранный пояс и время ближайшего запуска в нём.

### CRON-06. Ручной запуск

В UI владельцу доступна кнопка «Запустить сейчас». Она создаёт новую задачу
с сохранённым prompt расписания в том же чате и workspace. Применяются обычные
правила контекста, доступа, инструментов, HITL и guardrails. Ручной запуск
не меняет cron-выражение, часовой пояс или время следующего запуска по расписанию.

Пока в чате есть активная задача, включая любое ожидание, кнопка недоступна.
Сервер проверяет занятость независимо от состояния UI и атомарно принимает
новую задачу. Если чат успел заняться, действует TASK-02: попытка завершается
как failed с причиной CONTEXT_BUSY, без выполнения и очереди.
Текущая задача продолжает работу. Если ручная задача ещё активна к очередному
cron tick, автоматический запуск пропускается по CRON-02.

### CRON-07. Изменение расписания

Изменения prompt, cron-выражения и часового пояса применяются только к будущим
запускам. При приёме задачи сохраняется согласованный снимок этих параметров;
уже принятая задача продолжает работу с исходным заданием, включая выход
из ожидания и восстановление после restart. Редактирование расписания
не подменяет её prompt и не добавляет ей follow-up.

Следующие автоматические и ручные запуски используют новые сохранённые
параметры. Само редактирование не запускает задачу и не выполняет пропущенные
запуски задним числом. При гонке редактирования с приёмом запуска задача
получает целиком одну версию параметров, без смешивания старых и новых полей.
Правила изменения политики инструментов из TOOL-01 и HITL-03/04 сохраняются:
снимок расписания не закрепляет устаревшие разрешения.

## 9. История чата и суммаризация

### CONTEXT-01. Контекст между задачами

Новая задача получает релевантное summary чата, последние сообщения и новую
инструкцию. Это относится и к повторным cron-запускам. Один `contextId` без
подключения истории не обеспечивает требуемую непрерывность.

### CONTEXT-02. Семантическое summary

Суммаризация должна осмысленно сохранять цели, ограничения, решения, последние
уточнения, подтверждённые результаты, ошибки и открытые вопросы. Старое решение,
заменённое новым, не должно оставаться действующим только потому, что оно раньше
встретилось в истории. Запланированное действие отличается от выполненного.

Текущая реализация `StructuredSummarizer` не вызывает модель и укорачивает
сериализованную историю с конца. Проведённая диагностическая проверка показала:
ранний длинный лог остаётся, а более поздний результат действия теряется.
Отдельная проверка двух задач в одной session показала отсутствие первой задачи
в контексте второй. Существующие проверки compaction подтверждают механику,
но не качество сохранения смысла.

### CONTEXT-03. Источник истины

- Полный transcript сохраняется, summary ссылается на исходные сообщения.
- Детали можно получить через retrieval с теми же ограничениями доступа.
- Состояния HITL, действий, ожиданий, deadline и окончательных timeout хранятся
  структурированно вне summary.
- Summary не выдаёт разрешение на инструмент и не открывает закрытое ожидание.
- Если нужна гарантия отсутствия повторного действия, её обеспечивает runtime
  state/идемпотентность, а не обещание модели помнить summary.
- Ошибка суммаризации не должна молча заменять предыдущий результат обрезанным
  текстом и терять актуальные ограничения.

## 10. Guardrails от prompt injection

### GUARD-01. Проверка и решение владельца

Недоверенные сообщения, файлы, ответы инструментов и внешних агентов не могут
подменять системные правила и расширять доступ. Если механизм guardrails
считает содержание подозрительным, решение передаётся владельцам в том же чате.
Одобрение относится к использованию конкретного материала в текущих правах;
оно не отключает серверную policy или изоляцию данных.

Согласованный LLM-детектор и места проверки описаны в §12.3.
Нельзя обещать обнаружение всех prompt injections. Независимо от
детектора должны действовать серверная авторизация, tool policy, изоляция
и защита секретов.

### GUARD-02. Отказ владельца от использования материала

Если владелец отклонил подозрительное сообщение, файл или результат инструмента,
агент не использует этот материал. Основная модель получает структурированное
уведомление об отказе с идентификатором/типом источника, без самого содержимого
и без цитирования подозрительных инструкций. Для tool result уведомление
заменяет отклонённый результат, сохраняя связь с исходным tool call.

Задача автоматически не переходит в `failed`. Агент может продолжить по
оставшимся разрешённым данным, выбрать другой допустимый способ решения или
запросить недостающую информацию. Он не должен выдавать отклонённый материал
за проверенный результат или придумывать его содержание.

Решение связывается с конкретным материалом и его версией.
Ограничение действует и при последующих обращениях: материал не возвращается
модели через summary, memory, retrieval, повторное чтение файла или другой
инструмент. Для подозрительных файлов нужен карантин вне доступной Bubblewrap
папки; одного удаления текста из model context недостаточно. До разрешения
содержимое не должно поступать в основную модель или вызываемые ею инструменты.
Если материал сохраняется для истории/проверки владельцами, такое хранение
не делает его доступным agent loop; сроки хранения определяются отдельно в Q8.

### GUARD-03. Таймаут решения владельца

Срок ожидания решения guardrails настраивается; по умолчанию он составляет
24 часа с момента создания запроса владельцам. Абсолютный deadline сохраняется
в durable state и не начинается заново при restart, переподключении UI или
поступлении follow-up.

Если решение не получено вовремя, материал остаётся недоступным по правилам
GUARD-02. Основная модель получает уведомление «Срок ожидания решения по
материалу истёк; использовать материал нельзя» без его содержимого. В истории
фиксируется timeout, а не отказ, якобы сделанный владельцем.

Агент может продолжить задачу по разрешённым данным; автоматического перехода
в `failed` нет. Для tool result сохраняется связь с исходным tool call.
Следующий model call получает также накопленные follow-up по TASK-03.
Одновременное решение владельца и срабатывание deadline должны фиксировать
один исход запроса и приводить к одному продолжению.

### GUARD-04. Ошибка или недоступность детектора

Если требуемую проверку выполнить не удалось, материал не считается проверенным
или автоматически разрешённым. В соответствующем чате создаётся запрос
владельцам с пометкой «Не удалось проверить материал», без утверждения,
что prompt injection уже обнаружена. До решения содержимое закрыто от агента.

Разрешение владельца позволяет использовать конкретный материал в существующих
правах. Отказ обрабатывается по GUARD-02. Ожидание настраивается и по умолчанию
составляет 24 часа; timeout обрабатывается по GUARD-03. Недоступность детектора
сама по себе автоматически не переводит всю задачу в `failed`.
Если проверка материала явно исключена настройкой TOOL-02, детектор для этой
области не вызывается и его недоступность не создаёт запрос guardrails.

## 11. Удаление artifact tools и исключённый объём

### CLEAN-01. Удаляемая функциональность

Полностью удалить `core_artifact_save`, `core_artifact_load`,
`core_artifact_list`, их регистрацию, схемы, handlers, model instructions

Если S3/MongoDB backend и зависимости используются исключительно этой

По анализу `pymongo` относится к dedicated artifact service; финальный список

Входящие вложения, использующие эту подсистему сейчас, сначала перевести на
папки чатов. Стандартные A2A Artifact для результатов задач, transport storage
и workspace snapshots имеют самостоятельное назначение и сохраняются там,

### SCOPE-01. Не включать

- Общую отдельную очередь HITL вместо запросов внутри чатов.

- Автоматическую отмену удалённой операции после timeout ожидания.

## 12. Предложение по реализации и совместимости

Использовать существующие A2A lifecycle, PostgreSQL workflow/inbox/outbox,
tool dispatch, recovery и audit. Не вводить вторую несовместимую task state
machine или новую БД ради этих функций. Durable ожидание не реализовывать
одним длинным sleep внутри worker.

Предлагаемый порядок независимых поставляемых частей:

1. Identity, owner role, разделение transport и chat scope; проверка изоляции.
2. Чаты, постоянные папки, вложения и базовый UI.
3. Tool policy, HITL и вопросы владельцам.
4. Durable remote A2A/wake-at и правила занятости чата.
5. Семантическое summary и перенос контекста между задачами.
6. Cron, guardrails и завершение UI настроек.
7. Удаление artifact tools после переноса зависимых flows.

Перед каждым изменением публичного или persisted contract описать миграцию:
привязку старых задач к чатам/identity, судьбу существующих файлов, добавление
ожиданий, совместимость remote-agent env configuration с настройками UI,
переключение endpoint-ов и откат. Автоматическое удаление старых пользовательских
данных не следует из требования убрать код artifact tools.

### 12.1. Изоляция исполнения через Bubblewrap — согласованный выбор

Один pod не требует общей видимости файлов для всех дочерних процессов.
Общий доверенный сервер запускает Python, terminal и фоновые команды через
Bubblewrap. Папка чата сохраняется на постоянном томе; окружение исполнения
создаётся на время команды/сессии.
Для этого не нужен отдельный Kubernetes Pod на каждый чат.

Bubblewrap запускается с собственными mount/PID/IPC/network namespaces и
ограничением системных вызовов. Профиль задаёт доверенный runtime;
модель не может заменить его или запросить запуск без ограничений.
В файловое представление процесса включаются
только папка его чата как `/workspace`, отдельные временные файлы и нужные
системные программы/библиотеки для чтения. Общий корень чатов, данные сервера,
секреты и service-account token туда не монтируются. `/proc` должен относиться
только к изолированным процессам, а не открывать процессы сервера и соседних
чатов. Ненужные унаследованные дескрипторы закрываются.

Это не готовая гарантия от установки одного пакета: профиль запуска является
частью реализации и проверки. User namespaces должны быть доступны процессу
внутри pod; seccomp/AppArmor/SELinux и container runtime могут препятствовать
их созданию. Совместимость должна быть проверена на целевом кластере без
`privileged: true`, host runtime socket и широких привилегий на узле.
Если Bubblewrap отсутствует или обязательные ограничения применить нельзя,
выполнение команды отклоняется с понятной ошибкой окружения до запуска
недоверенного кода. Автоматический запуск без sandbox запрещён.
Доступ к целевому кластеру для проверки пока не предоставлен; выбор механизма
не означает, что его совместимость с этим кластером уже подтверждена.

Существующий общий запуск в `execution.py` — точка применения ограничений
к terminal и Python, включая фоновые команды. Python tool broker уже использует
Unix-сокет; окружению предоставляется только сокет его собственного вызова,
а dispatch сохраняет привязку к задаче и общую policy/HITL. Broker не должен
принимать произвольный chat/tenant от недоверенного процесса.

Согласован прямой доступ Python/terminal в публичный интернет с запретом
доступа к внутренним сервисам и соседним чатам. Сетевая граница описана в §12.2.

Критерии проверки Bubblewrap: два одновременно работающих чата;
успешное чтение/изменение своего файла и отказ для чужого; невозможность доступа
через `/proc`, symlink, чужой broker socket и дочерний subprocess; отсутствие
platform secrets; прекращение всего дерева процессов при timeout; явная ошибка
старта исполнения, если обязательный sandbox недоступен. Изоляция файлов
не равна полной изоляции ресурсов: CPU, память и лимит процессов внутри общего
pod следует ограничить отдельно. Общее ядро остаётся границей доверия.

### 12.2. NET-01. Публичный интернет и закрытая внутренняя сеть

Python, terminal и их дочерние процессы могут обращаться в публичный интернет,
в том числе через `requests`, `curl` и менеджеры пакетов. Отдельный перечень
разрешённых публичных доменов не требуется. Установка пакетов сохраняет общую
tool policy/HITL и записывает файлы только в разрешённую область чата.

Трафик sandbox проходит через контролируемый выход из его network namespace.
Нельзя просто разделить с ним сеть серверного процесса или положиться только
на переменные `HTTP_PROXY`/`HTTPS_PROXY`: произвольный код не должен обходить
границу прямым socket-соединением. Профиль запуска и сетевые правила нельзя
изменить из sandbox.

Недоступны приватные, link-local и иные непубличные назначения, адреса соседних
окружений, Pod/Service/node сети кластера, внутренние API и metadata endpoints.
Защищённые адреса конкретного развёртывания учитываются явно, в том числе если
они используют публичный диапазон. Нельзя достичь localhost серверного pod
через адрес шлюза или иной маршрут; loopback внутри собственного sandbox
остаётся локальным этому окружению.

Ограничение проверяет фактический адрес назначения каждого соединения, включая
переходы по redirect и изменение DNS-ответа. Оно распространяется на IPv4 и
IPv6 и не обходится альтернативным представлением адреса или протоколом.
DNS для публичных ресурсов должен работать через контролируемый resolver;
это не открывает произвольный доступ к внутренней сети.

Защищённый сервер сохраняет необходимый ему доступ к PostgreSQL, Keycloak,
MCP и доверенным A2A endpoints. Доступ sandbox к такому инструменту возможен
через собственный broker после проверки policy/HITL; сетевые credentials
сервера процессу не выдаются.

Инженерный вариант для проверки: Bubblewrap network namespace и принудительный
шлюз выхода в сеть с фильтрацией назначений. Userspace networking, например
slirp4netns, может дать непривилегированному namespace выход в интернет,
но само по себе не является политикой блокировки всех внутренних адресов.
Конкретный компонент шлюза, поддерживаемые протоколы и способ фильтрации должны
быть определены и проверены до реализации этого среза; HTTP-only proxy нельзя
выдать за универсальный прямой сетевой доступ.

Обычная Kubernetes NetworkPolicy применяется к pod и может быть дополнительной
границей, но не заменяет разные права сервера и чатов внутри одного pod.
При отказе сетевого контроля нельзя переключаться на неограниченную сеть pod.

### 12.3. Универсальный LLM-детектор prompt injection — согласованный выбор

Для первой версии используется отдельный LLM-вызов классификации через
существующий model adapter. По умолчанию используется подключённая модель
агента; модель и её подключение для
guardrails должны настраиваться отдельно. Это отдельный короткий контекст без
tools, полномочий исполнения, секретов и истории других чатов. Обучение новой
модели, собственный inference server и новый pod для этого варианта не нужны.

Основание выбора — переиспользование текущей интеграции и универсальная политика
проверки без привязки к конкретной предметной области. По решению пользователя
оценка качества на наборе данных, benchmark и подбор модели по их результатам
не входят в объём работ и не являются условиями приёмки. Точность детектора
не измеряется; преимущество над другими моделями и полнота обнаружения атак
не заявляются.

Сравнение рассмотренных вариантов по первичным источникам:

| Вариант | Возможность | Ограничение для нашего сценария |
| --- | --- | --- |
| Отдельная LLM-проверка | Проверка по заданной политике; такой подход документирован в NeMo Guardrails | Качество зависит от модели и prompt; дополнительные latency и token cost; модель тоже может поддаться атаке |
| Meta Llama Prompt Guard 2 86M | Специализированный многоязычный классификатор injection/jailbreak | Окно 512 токенов; нужен анализ фрагментов; русский отсутствует в опубликованном списке языков оценки |
| ProtectAI DeBERTa v3 prompt-injection v2 | Специализированный классификатор | Карточка указывает английский язык и отсутствие обработки неанглийских запросов; проект помечен как архивный |

NeMo Guardrails можно использовать как framework, но он не требуется только
ради одного классификационного вызова при наличии собственного runtime.
Добавление framework в зависимости не предусматривается.

Порядок проверки:

1. Доверенный runtime определяет источник и конкретную версию материала.
   Детектор получает тип источника и минимальный относящийся к задаче контекст,
   чтобы различать пользовательское уточнение и инструкции из чужого документа.
2. Перед передачей основной модели проверяются новые входящие сообщения,
   извлечённое содержимое файлов и результаты tools/A2A; перед dispatch —
   аргументы вызова. Исключения TOOL-02 применяются к аргументам и результатам
   конкретного инструмента, но не отключают проверки входящих сообщений/файлов.
3. Отдельный запрос с фиксированной политикой ищет попытки подменить инструкции,
   изменить задачу через недоверенный источник или обойти права/изоляцию.
   Обычные просьбы написать код и цитирование примера атаки сами по себе
   не должны считаться основанием для блокировки.
4. Runtime валидирует структурированный ответ детектора. «Подозрение не найдено»
   позволяет продолжить обычные проверки; подозрение или неуверенный результат
   передаётся владельцу. Это не выдача инструменту разрешения на выполнение.
5. Пустой, повреждённый ответ, timeout API или неполная проверка обрабатываются
   по GUARD-04. Произвольный текст ответа классификатора не становится новой
   инструкцией основной модели.

Для длинных документов проверяется извлечённый текст по фрагментам с перекрытием
и учётом границ документа. Проверка только первых токенов, обрезание хвоста или
проверка одного summary не дают статуса «проверено» всему исходному материалу.
Если формат не поддерживается, извлечение неполно или исчерпаны лимиты времени
и токенов проверки, материал считается непроверенным и идёт к владельцу.
Приём файла до 25 МБ не означает, что все его байты помещаются в контекст LLM.

Для guardrails отдельно учитываются расходы и задержка. Их вызовы не являются
рассуждением основного агента, но требуют ограниченного бюджета; бесконечные
повторы проверки недопустимы. Ожидание владельца использует ранее согласованный
durable flow и 24-часовой настраиваемый timeout.

Для приёмки проверяется механика интеграции: отдельный контекст и настройка
модели, валидация ответа, обработка вердиктов/ошибок, исключения TOOL-02,
HITL, timeout и сохранение ограничений доступа. Эти проверки используют
заданные ответы детектора и не оценивают точность классификации реальных
или синтетических материалов. Runtime учёт расходов и задержки сохраняется;
это эксплуатационная наблюдаемость, а не benchmark качества.

## 13. Критерии приёмки для будущих автоматических сценариев

| ID | Дано / действие | Наблюдаемый результат |

| AC-63 | В сообщении UI или A2A одно из нескольких вложений не загрузилось, не сохранилось либо превышен общий лимит, в том числе после загрузки первых файлов | Всё сообщение отклонено с причиной; текст и частичные вложения не передаются агенту и не публикуются в workspace, включая после restart; существующие файлы и активная задача сохранены |

Проверки конкурентности должны действительно создавать гонку. Перезапуски
проверяются с PostgreSQL и сохранёнными файлами. Для суммаризации нужны случаи
с поздними исправлениями, длинными логами и повторной compaction; проверка
наличия заголовков summary недостаточна. Для guardrails проверяются механика
интеграции и обработка заданных вердиктов; оценка качества детектора на наборе
данных исключена из объёма по §12.3.

## 15. Источники и перенос в нормативную спецификацию

- [A2A 1.0: multi-turn interaction](https://a2a-protocol.org/v1.0.0/specification/#34-multi-turn-interactions): различие `contextId` и `taskId`.
- [A2A 1.0: TaskState](https://a2a-protocol.org/v1.0.0/specification/#413-taskstate): терминальный `TASK_STATE_FAILED`; правило `CONTEXT_BUSY` является контрактом нашего приложения.
- [Keycloak Server Administration](https://www.keycloak.org/docs/latest/server_admin/): service accounts и настройки срока токенов.
- [Keycloak OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers): introspection и token endpoints.
- [Bubblewrap](https://github.com/containers/bubblewrap): user namespaces, mount/PID/IPC isolation и ответственность вызывающего за профиль безопасности.
- [Kubernetes: Linux kernel security constraints](https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/): seccomp, AppArmor/SELinux и ограничения privileged containers.
- [Kubernetes Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/): область действия сетевых правил — выбранные pod.
- [slirp4netns](https://github.com/rootless-containers/slirp4netns): userspace networking для непривилегированных network namespaces; кандидат для проверки, не выбранная готовая security policy.
- [NeMo Guardrails: LLM Self-Check](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/self-check): подход с отдельной LLM-проверкой; framework не входит в выбранную реализацию.
- [Meta Llama Prompt Guard 2 86M](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M): назначение, окно 512 токенов и опубликованные языки оценки.
- [ProtectAI prompt-injection v2](https://huggingface.co/protectai/deberta-v3-base-prompt-injection-v2): ограничения по языку и отметка об архивировании проекта.
