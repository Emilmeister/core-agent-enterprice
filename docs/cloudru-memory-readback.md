# Read-only inventory памяти в Cloud.ru

Этот шаг проверяет сохранённые размерности и определения индексов в целевой БД.
Он нужен для открытого memory gate в
[плане миграции](superpowers/plans/2026-10-24-cloudru-main-parity.md).
Не запускает embedding provider, миграции, backfill, DDL или запись данных.

Используйте существующее подключение к БД памяти с теми же `search_path` и
правами чтения, что у runtime. Пример для заранее настроенного локального
libpq service; пароль хранится в штатном private credential store, не в команде:

```sh
psql 'service=core_agent_memory' -X -qAt \
  --set=tenant_id='DEPLOYMENT_TENANT_ID' \
  --set=app_name='EFFECTIVE_AGENT_NAME' \
  --set=user_id='AUTHENTICATED_OWNER_ID' \
  --set=namespace='subject/AUTHENTICATED_OWNER_ID' \
  --file=deploy/cloudru-memory-readback.sql > memory-readback.json
```

Замените четыре значения подтверждённым scope нужной памяти. Runtime использует
tenant развёртывания, эффективное имя агента и authenticated identity, а не
отображаемое имя владельца. Для памяти чата namespace равен `session/<contextId>`;
для пользовательской — `subject/<identity>`. Фильтры всех четырёх полей обязательны.
SQL variables подставляются как quoted literals; не заменяйте их raw interpolation.
Если платформа предоставляет только SQL/job UI, оператор запускает этот же файл
через доступный `psql` workflow; доступ к действующему Kubernetes не требуется.

Файл содержит один JSON-объект: время, версии сервера/pgvector, точную таблицу и scope,
число документов по размерностям и определения индексов этой таблицы.
Содержимое документов, IDs, пути и значения векторов не выводятся.
Транзакция `REPEATABLE READ READ ONLY` завершается rollback; timeout ограничивает
каждый запрос 15 секундами, ожидание блокировки — 2 секундами.
При ошибке `psql` возвращает ненулевой код; такой
результат не считается успешной проверкой. При timeout нельзя удалять лимит
ради зелёного результата: оператор выбирает подходящее окно для чтения.

Сопоставьте размерности с фактическими `EMBEDDING_MODEL`, `EMBEDDING_API_BASE` и
`EMBEDDING_DIMENSION` работающего экземпляра, без ключей. Индекс должен быть
valid/ready, а его expression и predicate — соответствовать нужной размерности.
Наличие индекса для 1024 не доказывает покрытие строк с 2048. Пустой corpus либо
нулевой результат при ошибочном scope не подтверждает совместимость данных.

Этот inventory не доказывает использование индекса реальным поиском, качество
выдачи или модель, создавшую старые векторы: per-vector model provenance в текущей
схеме нет. Для завершения gate остаются план реального запроса из
`PostgresMemoryStore.vector_candidates`, проверка выдачи и подтверждённая история
модели/пересчёта corpus. Не меняйте модель или размерность и не пересоздавайте
индекс по одному этому отчёту. Локальный прогон SQL подтверждает только сам
инструмент чтения; целевой отчёт должен получить оператор из Cloud.ru.
