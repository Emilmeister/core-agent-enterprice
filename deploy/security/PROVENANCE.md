# Sandbox OCI profiles

`oci-amd64.json` and `oci-arm64.json` are generated native-architecture OCI
profiles for the trusted server/Bubblewrap supervisor. They are not the inner
application seccomp policy and do not alone make arbitrary code safe.

The vendored baseline is [moby/profiles default.json at
6fe7deb1b9fb7c0397a4593480d7d22b9ee8caef](https://github.com/moby/profiles/blob/6fe7deb1b9fb7c0397a4593480d7d22b9ee8caef/seccomp/default.json),
licensed under Apache-2.0; its unmodified license is
`upstream/LICENSE-moby`. `upstream/moby-default.json` preserves source bytes.
`SHA256SUMS` pins both source and generated bytes. Builds never fetch a moving
upstream branch.

The generator resolves Moby's Docker-specific `includes`/`excludes` predicates
for the specified native architecture, an empty capability set and Linux 6.3+.
Only its known `minKernel=4.8` predicate is accepted. Native-only OCI architecture
lists deliberately do not enable x86/x32/ARM compatibility ABIs. Unknown future
kernel predicates stop generation for review.

The final explicit allowance for `clone`, `unshare`, `setns`, `mount`, `umount2`
and `pivot_root` permits trusted nested namespace/bootstrap operations. Pod user
namespaces and a second inner application seccomp policy are mandatory; never
run untrusted commands directly under only this outer profile. `clone3` retains
the baseline ENOSYS result for libc fallback. No Pod capabilities are added.

Regenerate from the repository root with:

```sh
uv run --no-sync python deploy/security/generate-oci.py
```

The image copies these files to `/opt/core-agent/security`, verifies checksums,
rejects symlinks and removes write permissions. The operator installs the native
OCI file beneath the node kubelet seccomp directory before creating the Pod.
The agent Pod does not mount or modify that node directory.

The separate `core_agent/sandbox-policy.json` is packaged with the Python module
and copied beside these profiles in the image. It is integrity-checked by the launcher;
it is intentionally not regenerated or re-hashed by this OCI generator.

CI uses [kind v0.33.0](https://github.com/kubernetes-sigs/kind/releases/tag/v0.33.0)
with the release's pinned multi-architecture Kubernetes 1.37.0 node digest.
`deploy/kubernetes/kind.sha256` pins the native Linux executables. The amd64/arm64
jobs use native [GitHub-hosted Linux runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
This job's presence does not certify either architecture until it passes.

The named AppArmor supervisor profile and host deployment instructions are in
[`../kubernetes/apparmor/`](../kubernetes/apparmor/README.md). AppArmor is a
separate host policy; it does not replace either of these OCI/inner seccomp
policies. Its source is checked in directly, rather than generated by the OCI
generator. Load only the named profile and keep existing host profiles intact.
